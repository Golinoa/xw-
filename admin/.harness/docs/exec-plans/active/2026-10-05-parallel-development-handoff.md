## 阶段二：业务模块前后端并行门

阶段一相应基础门禁通过后，按运营后台实施计划的业务顺序逐域调度。每个域使用同一契约版本并遵循以下握手：

1. `udone` 后端会话核对 PRD 需求编号、权限和现有实现；确定运营 API 的实际命名空间及版本，并在唯一后端真源定义 endpoint、输入/输出、错误、分页/排序、权限、幂等/冲突语义和兼容策略。涉及数据时先设计 migration、约束、RLS、测试。
2. 后端负责人发布可审阅契约版本/提交号、虚构 fixture 和验收条件。尚未实现的业务可先提供隔离的 typed fixture/mock adapter 给前端；mock 只支撑 UI，不得冒充已联调或生产 API。
3. `~admin` 会话根据该契约生成或更新 API client，并实现页面、状态、权限呈现与浏览器测试；不复制后端类型源、不直接访问运营表。
4. `udone` 由单一责任会话串行维护运营迁移、RLS 与 schema 真源，运行本地数据库/API 测试。契约变更先通知前端并升级契约版本，再同步 client 和测试。
5. 两端分别完成本端门禁后进行真实集成验收；区分 mock、local、staging 证据。真实 staging 操作仅按已批准环境流程执行。

业务配对顺序沿用 `~admin` 实施计划：运营身份/应用壳 → 客户与产品合同 → 账款 → 授权与租户交付 → 私有化部署与售后 → 账号/权限/审计/总览 → 集成与发布验收。此顺序不自动授权跳过每域契约和数据库/RLS验收。

## 文件所有权与并发规则

| 文件/领域 | 唯一写入方 | 另一端处理方式 |
|---|---|---|
| Vben workspace、前端页面/client/路由、前端 CI/部署 | `~admin` | `udone` 不复制前端代码或 workspace 配置。 |
| Hono 路由/服务、运营 API 真源与共享后端契约 | `udone` | `~admin` 只消费已发布契约/client。 |
| Supabase migration、运营 schema/RLS/RPC、pgTAP、生成 schema 报告 | `udone` | `~admin` 不建影子 schema、不直接访问受保护表。 |
| 两端 PRD/架构/工程规则 | 各自项目负责人 | 跨系统决策先落后端事实真源，再更新前端消费说明与索引。 |
| 同一业务域 API 契约及迁移 | 同一时刻一个 `udone` 责任会话 | 先冻结契约，再让前端并行实现。 |

禁止两个会话同时改同一仓库的根 manifest、lockfile、CI 或同一份 harness 规则。跨项目边界明确不等于允许共享同一个工作树；建议使用各自独立分支/工作区。

## 调度器协议

调度器只负责拆分、派发和等待，不审查代码、不读取项目源码、不代替执行任务。启动后维护两条有序链：

1. **运营前端链：**运营后台实施计划 Task 1 → Task 2 → Task 3 … → Task 9。
2. **后端链：**ERP 实施计划 Task 1 → Task 2；之后仅按运营后台实施计划 Task 3–9 中明确归属 `udone` 的工作创建后端对话。ERP 计划 Task 3–8 是旅行社 ERP 功能，不因本次运营后台开发而自动纳入调度。

启动时分别为两条链创建独立 Codex 对话，只派发各自当前第一个 Task。不同仓库中互不冲突的当前 Task 可并行等待；同一条链绝不越序。每项 Task 完成后，按完成汇报更新调度状态，再向该链创建下一条独立对话并发送提示。遇到运营后台某个跨端 Task 时，可把计划规定范围拆成 `~admin` 前端对话和 `udone` 后端对话；必须先有可引用的后端契约，且两端都报告完成后才可派发该计划的下一 Task。

调度器不得进行代码阅读、diff 审查或自行补做 Task。以执行对话提交的完成汇报作为等待/调度依据；汇报须包含修改文件、验证结果、提交号和工作树状态。若 Task 自身未完成、未提交或仍有 Task 自身的未提交改动，暂停该链，不派发后续 Task。仅在执行对话已完全停滞/明确阻断时介入，做简单的阻断判断并优先通过新的执行对话处理；不得借机扩展为审查。不得要求执行对话提交无关 WIP；若任务开始时工作树已有无关改动，必须保留它们，将自身改动独立提交，并在完成汇报中区分基线 WIP 与 Task 改动。只要求 Task 自身改动提交且无遗留；不可为追求全仓 clean 清理旧改动。

### 每个执行对话的派发提示

创建每个执行对话时，将以下文本中的占位符替换为当前项目、计划文件和 Task 编号；一次只包含一个 Task。跨端 Task 要注明该对话负责的端及计划规定的文件边界。

```text
请执行《{计划路径}》的 Task {N}（{项目/负责端}）。开始前阅读当前 AGENTS.md、详细计划中对应的 Task、相关代码与测试，并检查 git status；保留工作区中的无关改动。严格按照该 Task 规定的目标、范围、文件、完成标准和批次特殊要求执行，只完成当前 Task，不提前实施后续 Task，也不要扩大重构范围。优先复用现有稳定实现，补齐该 Task 要求的测试、文档或代码。若该 Task 明确只做测试、文档或验证，就遵守该边界，不自行增加实现。按详细计划和 AGENTS.md 的要求完成 review、验证及进度记录，并修复当前 Task 引入的问题。完成后提交本 Task 自己的改动；不要提交或清理无关 WIP。汇报本 Task 完成情况、修改文件、验证结果、提交号、工作树状态，以及留给后续 Task 的内容。未完成或受阻时明确说明阻断点，不得提前标记完成。
```

执行对话的明确范围优先于模板中的通用措辞。例如 `udone` Task 1 的 staging 验证只在该环境已经获准时执行；`~admin` 尚未建立 Git 仓库时，前端链先处理独立 Git 仓库/分支这一前置条件，再开展需要提交的 Task。提交无法完成时如实报告并暂停该链，不伪造提交号或清理无关文件。

### 后续调度边界

- 每次派发前先阅读两端最新 journal、详细计划状态、当前执行会话/工作树记录，确定是否已有该 Task 在执行；不得重复派发正在进行或已完成的任务。
- 当前优先闭环已开始的 Task 9：解决空库迁移版本冲突和前端运行内存故障，保留现有未提交变更；随后补齐计划要求的真实环境/浏览器验收证据。未收到执行者完成报告前，不派发后续业务 Task。
- 一个 Task 完成并具备后续条件后，按依赖顺序只派发下一项；跨端业务先冻结后端契约，再分派前端实现；两端报告完成后才推进该业务域。
- 代码批次派发模板必须包含：开始前读 ERPNext 对应源码及测试、写下采纳/不采纳决策和验证断言；按端执行质量门；保留 WIP；汇报修改文件、命令/结果、提交号、工作树和未验证项。
- 调度器遵循本文件及两份详细计划的执行职责边界。计划更新只规定步骤和门槛，不代表已执行、已通过或已部署；完整验收仍需要相应环境证据。
