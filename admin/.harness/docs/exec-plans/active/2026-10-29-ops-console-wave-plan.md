## 二、为什么需要重排

原计划是**单轨串行瀑布**：`Task 3→4→5→6→7→8→9`，每个 Task 隐含「前后端同时完成」才算完成。实际推进中暴露三个结构性问题：

1. **完成口径过粗，导致任务无法关闭也无法推进。** Task 4/5 的前端已可用，但因后端未实现，「完成」条件永不满足，任务长期悬在 in_progress；Task 6/7/8 又因「依赖后端」而不敢启动。前后端进度差被传导成整体停滞。
2. **基础设施缺口不归属任何 Task，长期悬空。** e2e 假绿在 Task 2 遗留、Gitee CI 在 Task 2 遗留，但两者的验收又挂在 Task 9，中间无人认领。结果是 171 个单测在保护代码，却没有任何东西保护「页面真的能打开」。
3. **契约已冻结但未被当作可开发依据。** `Docs/ops-api-contract.md` 已定义 43 表 / 112 端点，前端完全可以在其上先行开发，却因为「等后端」而空转。

## 三、新推进原则

### 原则 1：双轨完成度，禁止用桩验证冒充任务完成

每个 Task 拆为两个可独立判定的状态：

| 状态 | 判定条件 | 谁来判定 |
| --- | --- | --- |
| `frontend-ready` | 页面、状态覆盖、组件测试、类型与 lint 全绿，基于契约桩可运行 | 本会话可判定 |
| `integration-ready` | 真实 API 联调通过；后端 pgTAP/RLS/拒绝路径测试通过；staging 双身份验收 | **必须后端与环境就绪后才可判定** |

**硬规则：**`frontend-ready` 不等于原计划 Task 完成，不得勾选原计划复选框。原计划复选框只在 `integration-ready` 达成后勾选。桩验证必须在页面、journal、交付报告中三处都标注「开发态契约桩」。

### 原则 2：基础设施先闭合

e2e 与 CI 前移为阶段 0。理由：它们保护后续每一个批次，越晚补代价越高；且不依赖后端，是当前唯一「零阻塞」的高价值工作。

### 原则 3：契约即开发依据，但契约变更必须是双向的

前端只消费契约，不发明字段。所有「契约未定义、前端按推导实现」的点，必须集中登记到该域 `README` 与 journal 的「待后端确认」表，供后端一次性对齐。契约若被后端修正，前端按修正值回归，不得兼容旧推导。

### 原则 4：源码参考门不豁免，但可批量执行

原计划要求 Task 3–9 每批次编码前读 ERPNext 源码与测试并写 journal。新流程保留该门，允许**同一阶段内一次执行覆盖该阶段全部批次**，但结论必须逐任务列出，不得合并成一句「已参考」。

## 五、阶段验收口径

### 阶段 0
- `pnpm run test:e2e` 真实执行任务，非 0 total；用例覆盖登录成功/失败、未登录重定向、无权限落 404、登出清理。
- 浏览器二进制实际可用（记录版本）。
- Gitee 流水线文件存在且 schema 合法；**明确标注**：文件存在 ≠ 分支保护已启用，该步需人工在仓库设置完成。
- 依赖审计输出分级结论：可安全升级 / 需随主框架升级 / 接受风险并说明理由。

### 阶段 1–3
- 每域交付：API 客户端（严格按契约字段名）、页面、七类状态覆盖（loading/empty/error/validation/permission-denied/conflict/destructive-confirm）、组件测试。
- 五门全绿：`quality:toolchain`、`format:check`、`lint:check`、`typecheck`、`test:unit`。
- 高风险动作（`isHighRiskPermission()` 为真）必须有二次确认 + 受影响摘要 + 必填原因。
- journal 含：源码参考门结论（逐文件）、契约推导待确认表、验收命令真实输出。
- **不勾选原计划复选框。**

### 阶段 4–5
不在本会话判定。需后端交付后另立批次。

## 六、明确不做（边界）

1. 不实现 `udone` 的 ops schema、迁移、RLS、API —— 已由业务端会话承接。
2. 不做 staging 双身份验收、性能基线、恢复演练 —— 无环境与合成数据。
3. 不升级主框架（Vite/Vue 大版本）来消 advisory —— 风险高于收益，列为独立专项。
4. 不用桩数据冒充联调通过，不在生产构建保留任何 stub 入口。
5. 不为「让门禁变绿」而放宽规则；放宽必须写明理由与影响面（如单文件超时上限）。

## 七、风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 后端契约与前端推导不一致 | 阶段 4 返工 | 每域维护「待确认表」，后端交付时逐条对齐；字段名以契约为准，前端不改契约 |
| 契约桩逻辑与真实后端行为偏离 | 桩验证通过但联调失败 | 桩只实现契约显式定义的行为，未定义处不臆造成功路径 |
| e2e 依赖 dev server 稳定性 | 用例抖动 | webServer 复用本地实例，失败重试 1 次，trace 仅在重试时采集 |
| 领域页面模式复制导致技术债 | 后续难改 | 阶段 1 先抽公共列表/表单/高风险确认模式，阶段 2/3 复用而非复制 |
| 依赖审计长期挂红 | 质量门整体无法宣告达标 | 阶段 0 出分级结论，明确「当前接受的风险」与「必须随框架升级」两类，不假装已解决 |
