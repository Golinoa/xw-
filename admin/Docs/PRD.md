# 有单软件运营后台产品需求文档（PRD）

- 项目标识：`~admin`
- 产品名称：有单软件运营后台（暂名）
- 版本：1.0
- 日期：2026-10-05
- 状态：已定稿
- 适用对象：产品、设计、前端、后端、测试和运营人员

> 本文定义软件提供方内部运营后台的产品范围、业务规则和验收标准。该后台与旅行社员工使用的 `udone` ERP/OMS 是不同产品边界。本文中的业务规则是本项目的规划基线；它不反向描述或改变 `udone` 现有行为。

## 参考项目依据

- [`udone` 技术选型](../../udone/Docs/TECH_SELECTION.md)：前端、Hono/Cloudflare Workers、Supabase、认证、RLS 和部署约束。
- [`udone` 架构说明](../../udone/ARCHITECTURE.md)：分层依赖、API 与数据库职责、租户上下文和模块边界。
- [`udone` 产品需求](../../udone/Docs/REQUIREMENTS.md)：旅行社业务范围，用于划清运营后台与旅行社 ERP 的职责。

以上文档只提供技术和边界参考。旅行社客户、订单、财务和审批规则不会自动成为运营后台需求；如需跨系统操作，必须经本 PRD 定义的接口边界。

## 1. 产品概述

### 1.1 产品目标

建立供软件提供方内部人员使用的运营后台，管理旅行社软件的商业客户、合同、商品与套餐、SaaS 订阅、私有化授权、线下收款、租户开通、私有化部署台账和售后服务。

系统面向软件销售和交付生命周期，不承担旅行社日常经营。旅行社员工仍在 `udone` 中处理客户、线路、订单、游客、应收应付、审批和经营报表。

### 1.2 首期结果

首期交付后，内部人员应能够：

1. 建立并维护已签约软件客户及其联系人。
2. 维护统一的软件产品目录、套餐和功能权益，并区分 SaaS 与私有化销售方式。
3. 登记合同、订单、付款计划和线下收款；支持分次收款、核销和退款登记。
4. 依据已审核合同创建或调整授权权益，并通过受控 API 为客户开通或变更 `udone` 租户。
5. 查看开通操作状态，安全重试失败操作，并保留完整审计线索。
6. 跟踪私有化部署实例、安装版本、授权有效期及人工升级记录。
7. 通过与客户、合同、产品和租户关联的服务工单跟进售后问题。
8. 通过总览及时发现即将到期合同/权益、逾期应收、待处理工单和租户同步失败。

### 1.3 设计原则

- **一份软件产品目录**：SaaS 与私有化共用产品定义，销售方式、计费方式、交付方式分别配置。
- **商业事实与运行事实分开**：运营后台记录客户签约、收款、合同权益和交付；`udone` 继续持有旅行社租户中的运营业务事实。
- **所有权变更可追溯**：合同、收款、权益、开通/停用、退款和私有化升级均可追溯到操作者、时间、原因和关联对象。
- **高风险动作需显式确认**：权益发放、延长、缩减、停用、恢复、退款登记和租户同步均显示影响摘要后确认。
- **以业务域模块化**：客户、商品、合同、账款、授权、交付、售后和审计各自拥有清晰职责；首期继续使用既有单体 API，不为模块拆分微服务。
- **默认安全拒绝**：页面隐藏不是权限控制；每个 API 操作和数据库访问都必须执行服务端授权。

## 2. 范围与边界

### 2.1 用户范围

仅面向软件提供方内部员工，不向购买软件的旅行社用户开放自助运营门户。

### 2.2 系统职责

| 信息/行为 | 运营后台职责 | `udone` 职责 |
|---|---|---|
| 软件客户、联系人 | 建立与维护商业客户档案 | 可保存与运营客户关联的旅行社组织标识 |
| 产品、套餐、价格与合同 | 维护销售定义及合同快照 | 不维护软件提供方的销售目录 |
| 收款、应收与退款记录 | 登记、审核和查询商业账款状态 | 继续维护旅行社自身的业务收付款 |
| 软件订阅、授权与功能权益 | 创建、调整和到期管理 | 执行已同步的租户有效状态与功能限制 |
| 租户内部用户、项目和业务 | 不直接编辑 | `udone` 内部系统真源 |
| SaaS 租户开通与权益同步 | 发起受控命令、展示结果、审计和重试 | 校验命令并创建/更新租户运行状态 |
| 私有化部署 | 记录实例、版本、授权和人工升级结果 | 不负责替运营后台管理私有环境凭据 |
| 售后工单 | 受理、分派、跟进和关闭 | 提供必要的租户状态和关联标识 |

不得通过运营后台直接修改 `udone` 的订单、游客、应收应付、审批、余额或旅行社内部用户数据。跨域操作必须走明确的 Hono API 契约。

### 2.3 首期包含

- 软件客户档案（从已签约/明确进入交付的客户开始，不含线索漏斗）。
- 产品、套餐、销售方式、价格版本和功能权益目录。
- 合同与订单基本管理、续约关联、合同状态记录。
- 应收计划、分次线下收款、核销、退款记录和账款查询。
- SaaS 订阅及授权权益快照。
- 经人工审核后调用 API 开通、延长、变更、暂停或恢复 `udone` 租户权益。
- 私有化部署实例和版本/授权/升级历史台账；实际部署由人员完成。
- 基础售后工单和处理时间线。
- 内部运营账号、角色授权、操作审计、集成操作记录和失败重试。
- 运营总览和按权限控制的列表、筛选、分页、导出能力。

### 2.4 首期不包含

- 线索获客、营销活动、销售漏斗、自动化邮件和完整 CRM。
- 面向客户的自助门户、客户自行下单、客户自行续费。
- 在线支付、银行自动对账、自动开票或电子发票平台接入。
- 电子合同签署、合同模板签署流和法律意见管理。
- 私有化环境的自动部署、远程升级、SSH 凭据保存或远程命令执行。
- 面向旅行社员工的 `udone` 功能实现或重做。
- AI 客服、智能体对话、呼叫中心和完整 SLA 自动化。
- 多币种换算与跨境结算。

## 3. 名词与核心概念

- **软件客户**：与软件提供方发生采购、合同、付款或售后关系的旅行社企业/组织。
- **`udone` 租户**：`udone` 中承载一家旅行社内部账号和业务数据的组织实例。它是运行系统概念，不等同于商业合同。
- **部署实例**：软件客户的一套运行环境；SaaS 客户至少关联一个 SaaS 租户，私有化客户可有一个或多个私有环境记录。
- **产品**：可销售的软件产品/版本线。
- **套餐**：针对一种销售方式定义的价格与权益组合。
- **合同**：软件客户与软件提供方确认的商业约定；签署后的合同内容不可被静默覆盖。
- **应收计划**：合同应收金额按约定日期拆分的账款条目。
- **收款记录**：内部登记的软件客户线下付款事实，不代表系统已代客户划款。
- **订阅**：具有起止时间和续订关系的 SaaS 商业权益。
- **授权**：允许特定客户/部署实例在指定期限和范围内使用产品的记录。
- **权益**：订阅/授权授予的功能、容量和期限约束。权益在合同生效时形成快照，后续产品目录修改不追溯改变已生效合同。
- **服务工单**：对某客户某产品/部署问题的可分派售后记录。

## 4. 用户与权限模型

### 4.1 用户类型

系统只接受软件提供方内部人员登录。旅行社租户员工不能因为拥有 `udone` 账号而自动取得运营后台权限。

运营账号首期使用独立运营账号池，并复用当前 Supabase Auth 项目。该方案是**身份和授权域逻辑隔离**，不是独立认证基础设施：同一个 Supabase 项目具有统一 Auth 用户空间。新建用户、邀请、重置、禁用、MFA 策略均由运营管理员控制，不提供公开注册。

### 4.2 首期角色

权限按动作授权，角色仅为一组权限的可维护集合。首期提供以下建议预置角色，管理员可按实际分工调整：

| 角色 | 默认职责 | 主要权限 |
|---|---|---|
| 平台管理员 | 内部账号和系统基础配置 | 运营用户/角色管理、字典配置、全域查询、审计查询；敏感操作仍需具体权限 |
| 商务运营 | 客户与合同生命周期 | 客户、产品目录读取、合同草拟/提交、续约、开通申请、工单查询 |
| 财务运营 | 应收与收款 | 应收计划、收款登记/核销、退款登记、账款报表；不默认拥有产品权益修改权 |
| 交付运营 | SaaS 开通与私有部署跟踪 | 租户映射、权益变更执行、部署台账和升级记录 |
| 售后支持 | 服务问题处理 | 客户/合同/租户只读、工单分派与处理；不得读取不必要的完整收款敏感信息 |
| 运营只读 | 管理层或审计查看 | 总览、报表和获授权的明细只读 |

角色名不作为硬编码业务逻辑。权限目录至少按 `customer.read/write`、`contract.read/write/approve`、`receivable.read/write`、`receipt.record/reconcile/refund`、`entitlement.read/request/approve/execute`、`tenant.provision/suspend/restore`、`deployment.read/write`、`ticket.read/assign/update/close`、`operator.manage`、`audit.read` 区分。

### 4.3 权限与账号要求

- 每个运营账号必须有启用状态和至少一个运营角色；无运营授权的 Auth 用户一律拒绝访问 `/ops` API。
- 前端路由、按钮和菜单按权限显示；服务端再次执行权限校验。
- 修改角色/权限仅平台管理员可做，并记录变更前后权限摘要。
- 高影响操作需记录原因；后端按权限和策略决定是否要求二次认证/MFA。
- 操作者不能通过可自行修改的 `user_metadata` 为自己提权；授权依据只能来自服务端维护的运营成员关系和可信声明。
- 账号禁用、撤销角色或退出后，旧会话不得继续执行新的受保护写操作；执行中的授权命令须能被查询和审计。
- 预留认证提供方适配边界；当安全或合规要求提高时，可迁移到独立 Supabase Auth 项目，不改变产品、合同和授权领域模型。

## 5. 信息架构

一级导航建议：

1. **运营总览**：核心指标、到期提醒、待办和同步异常。
2. **客户管理**：客户列表、客户详情、联系人、合同/订阅/部署/工单关联。
3. **产品与套餐**：产品目录、销售方式、套餐、价格版本、权益定义。
4. **合同与订单**：合同列表、合同详情、签约记录、续约和关联销售项。
5. **账款管理**：应收计划、收款登记、核销、退款、逾期和账款明细。
6. **订阅与授权**：SaaS 订阅、私有化授权、权益快照、变更历史和到期处理。
7. **租户交付**：`udone` 租户映射、开通/变更/停用命令、同步状态和重试。
8. **私有化部署**：部署实例、环境标识、软件版本、授权期限和升级历史。
9. **售后工单**：待受理、处理中、等待、已解决/关闭、工单时间线。
10. **运营配置**：运营账号、角色、系统字典和通知阈值。
11. **审计与集成**：关键操作审计、跨系统请求、失败任务和重试结果。

客户详情页作为商业关系聚合入口，按客户展示基本信息、合同、应收/收款、订阅/授权、租户、部署实例和工单；不复制 `udone` 内部业务明细。

## 6. 功能需求

### 6.1 运营总览（P0）

- 展示客户数、有效合同数、运行中 SaaS 租户数、有效授权/订阅数、逾期应收金额、即将到期权益数、未关闭工单数、失败的租户同步任务数。
- 默认到期窗口为未来 30 天；窗口值可配置，页面明确显示统计时间和口径。
- 点击指标进入相应列表，并继承当前用户的数据权限和默认筛选条件。
- 金额统计只包含已确认合同和已登记的收付款事实；待审核/待核销金额单独呈现，不计入实收。
- 图表和列表使用同一查询口径；空值、无权限、加载失败和部分服务不可用均有明确状态。
- 首页不通过逐条加载全部历史记录计算指标；汇总查询须分页、索引化或由后台聚合。

### 6.2 软件客户（P0）

- 建立、查看、编辑、停用客户档案；不提供无约束的物理删除。
- 客户核心字段：客户编号、企业名称、统一社会信用代码（如客户提供）、地区、业务联系人、电话/邮箱、来源说明、客户状态、负责人、内部备注、创建和更新时间。
- 联系人支持多条记录，标记主要联系人和使用场景；联系方式在列表中按最小必要原则展示。
- 客户编号唯一；企业名称和统一社会信用代码用于重复提示，不自动合并档案。
- 客户至少支持 `signed`、`onboarding`、`active`、`suspended`、`terminated` 生命周期状态；客户状态与合同、账款和租户状态彼此独立。
- 停用客户前展示关联合同、有效授权、部署和工单；禁止删除仍有关联商业事实的客户。
- 支持按名称/编号、状态、负责人、合同状态、授权到期范围搜索和筛选，服务端分页。

### 6.3 产品与套餐（P0）

- 产品目录维护产品编码、名称、描述、生命周期状态和可销售版本线。
- 每个产品可配置 SaaS 与私有化销售方式；未开放的销售方式不得签约。
- 套餐维护内部名称、客户可见名称、销售方式、计费类型、默认周期/授权期限、定价、包含权益、状态和生效区间。
- 支持周期订阅、固定期限授权和一次性授权三种可配置合同条目类型；不默认将一次性授权解释为永久免费更新或终身维护。
- 价格版本新增后只影响新合同；历史合同保存价格和权益快照。
- 权益按稳定功能键定义，支持启停、数值额度、期限和适用部署范围；产品显示名变化不得改变已发出的功能键。
- 套餐编辑不回写既有合同、已生效订阅和授权快照。
- 对套餐停用需检查草拟合同引用；已有生效合同仍可查看和续约，但是否允许续约受套餐状态明确控制。

### 6.4 合同与订单（P0）

- 从已存在客户创建商业合同/订单；不包含潜在客户线索、销售阶段漏斗和自动线索分配。
- 合同字段：内部合同号（唯一）、客户、销售负责人、产品/套餐/条目、销售方式、签约/生效/到期日期、合同币种与金额、付款条款、合同含税口径备注、商业备注、附件引用、状态和操作记录。
- 支持一份合同包含多个产品条目；各条目分别保存价格、销售方式、计费周期和权益快照。
- 合同状态至少为 `draft`、`reviewing`、`signed`、`active`、`expired`、`terminated`。收款状态独立计算，合同签署不代表已全额收款。
- 合同从草稿进入审核/签署/生效需权限控制；生效合同核心条款不可直接覆盖，修改通过变更单/续约记录形成新版本。
- 续约与原合同建立来源关系，记录续约前后期限、产品和权益差异；不得把续约当作改写原合同。
- 合同取消/终止需填写原因并预览关联应收、有效订阅/授权和租户影响；有财务或交付影响时须走对应撤销/停用流程，不物理删除历史。
- 合同金额使用明确币种；首期单份合同及其应收/收款分配只使用同一币种，不做汇率换算或多币种合并统计。税务口径按合同约定留档，首期不计算纳税义务、不自动开票。
- 合同附件可记录类型、文件名、上传人、时间和安全访问引用；附件不得通过公开可猜测 URL 暴露。签署电子合同不在首期。

### 6.5 应收、线下收款与退款（P0）

- 根据合同付款条款创建应收计划，支持一合同多期；每期含计划日期、金额、已核销金额、未收余额、状态和备注。
- 支持线下转账、现金或其他内部配置的方式登记收款；记录交易日期、金额、方式、流水/凭证号、登记人和凭证引用。
- 支持分次收款和一笔收款分配到多条应收；分配总额不得超过收款金额或应收余额，并使用数据库事务防止并发超额核销。
- 收款登记状态与核销状态分开；未审核/未核销记录不进入实收统计。
- 核销操作展示客户、合同、应收计划、金额和核销前后余额；撤销核销须有原因、权限、反向流水和审计记录，不覆盖原流水。
- 退款登记关联原收款/合同，记录金额、原因、日期、经办人和外部退款凭证；首期不调用银行/支付渠道发起退款。
- 账款状态由计划日期与已核销余额计算：未到期、部分收款、已收清、逾期；退款和冲销以独立流水呈现。
- 支持按客户、合同、到期区间、状态、负责人筛选；导出沿用相同权限与筛选。
- 首期不做在线支付、自动银行对账和自动开票。发票信息或已开票事实不得伪装成系统开票能力。

### 6.6 订阅、授权与权益（P0）

- 合同生效后，由有权运营人员基于合同条目创建订阅/授权草案；须审核后才能生效或发送给 `udone`。
- SaaS 订阅保存客户、产品、套餐、计费周期、起止时间、自动续订意向（首期仅记录，不自动扣费）、当前权益快照和状态。
- 私有化授权保存部署实例、授权方式、有效期/永久标志、维护期限（如合同约定）和权益快照；永久授权不得推导为永久软件更新服务。
- 权益快照支持功能键、启用状态、额度、期限和目标租户/部署实例；发放后不可静默覆写，只能新增变更记录。
- 支持申请新发、延期、升级、降级、额度变更、暂停、恢复、到期和撤销；每个变更保存来源合同、操作者、原因、审核结果、前后值摘要和同步结果。
- 变更前显示权益差异与目标客户/租户；高风险缩权、暂停、撤销和退款关联停用须二次确认。
- 到期提醒列入运营总览与待办；首期不自动扣费、不自动续约、不因合同到期而无人工复核直接删除数据。

### 6.7 `udone` 租户开通与变更（P0）

- 每个 SaaS 客户/产品可关联一个或多个 `udone` 租户实例；每个租户映射只能指向唯一商业客户，冲突时拒绝并提示。
- 运营数据保存外部租户标识、映射状态和同步版本；不复制旅行社业务表。
- 在审核通过后，通过 `udone` 现有 Hono API 的运营命令端点创建/绑定租户、激活/暂停/恢复租户或同步权益。API 端点和字段由后续技术规格定义，不在 PRD 中虚构物理接口。
- 命令须包含唯一幂等键、操作者、业务原因、合同/授权引用和期望版本；同一命令重试不得重复创建租户或重复应用权益。
- 同步状态至少包含 `pending`、`succeeded`、`failed`、`retrying`；保留最近请求摘要、响应摘要、请求 ID、重试次数和最后错误类别，不记录密钥或完整敏感载荷。
- 网络超时或结果不明时，先查询幂等命令状态再重试；不允许前端直接重复创建。
- 重试支持权限检查、失败类别提示、退避策略和操作审计；永久业务错误不得无限重试。
- 运营页面只展示租户状态/权益摘要；具体旅行社员工、订单、游客、财务信息由 `udone` 管理。

### 6.8 私有化部署台账（P0）

- 支持客户关联多个部署实例，记录实例名称/编号、部署类型、客户环境标识、当前版本、部署状态、授权关联、上线日期、维护到期日和负责人。
- 版本升级登记前后版本、执行日期、操作人、结果、影响说明和回滚备注；不声称通过后台完成了实际远程部署。
- 不在后台保存 SSH 密钥、数据库密码、主机 root 凭证或可以直接登录客户环境的秘密。
- 支持按客户、版本、状态、维护期限筛选，识别仍在服务期的旧版本实例。
- 私有化部署自动化、安装包托管和远程升级属于未来独立功能范围，需重新评估权限、网络和安全边界。

### 6.9 售后工单（P0）

- 创建与客户/产品/合同/租户/部署实例关联的工单，字段包括编号、主题、问题描述、问题类型、优先级、状态、负责人、创建/更新时间和关闭摘要。
- 问题类型至少支持使用咨询、故障反馈、数据/权限问题、部署/升级问题、合同/授权咨询；配置可扩展。
- 工单状态至少支持 `new`、`assigned`、`in_progress`、`waiting`、`resolved`、`closed`；等待状态需要等待对象或备注。
- 每次分派、状态变化、内部处理说明和对客户沟通摘要追加到不可覆盖的时间线；不得用编辑覆盖历史结论。
- 可关联租户同步任务、授权变更和部署升级记录，减少人工抄写并便于追踪。
- 工单超期提示按可配置的内部工作时限计算；首期不向客户承诺自动 SLA、不发送外部通知。
- 支持按负责人、优先级、状态、客户、产品和更新时间筛选；关闭工单可重新打开并记录原因。

### 6.10 运营配置、审计与集成（P0）

- 运营管理员管理账号邀请、禁用、角色和权限；禁止公开注册。
- 关键审计事件至少覆盖登录结果、授权变更、合同关键状态、收款登记/核销/退款、租户操作、私有化版本登记、角色变更和导出。
- 审计事件记录操作者 ID、动作、目标对象、时间、请求 ID、原因和前后值摘要；密码、访问令牌、完整支付凭证和不必要的个人敏感信息不得进入日志。
- 运营人员只能访问 `ops` 领域授权的数据；`udone` 租户用户不能访问运营 API，运营账号不自动拥有旅行社内部业务权限。
- 每个跨系统调用记录调用目的、关联商业对象、幂等键、目标系统、状态与可安全展示的结果摘要。
- 对失败命令提供授权后重试、取消尚未执行的命令和查看历史；成功执行的命令不可删除。
- 重大数据导出需单独权限，记录导出者、筛选条件、时间和导出对象范围。

## 7. 关键业务流程

### 7.1 已签约客户至 SaaS 开通

1. 商务运营创建或确认软件客户档案。
2. 建立合同，选择产品/套餐/SaaS 销售方式，生成合同条目和权益预览。
3. 合同签署状态确认后，登记付款条款与应收计划；收款由财务运营线下登记并分次核销。
4. 交付运营根据已签合同创建 SaaS 订阅和待开通权益；系统检查客户、产品、合同期限和重复租户映射。
5. 有权限人员审核开通申请，预览目标租户、权益和期限后确认。
6. 后台通过 API 提交幂等命令，`udone` 创建/绑定租户并返回结果；成功后更新同步状态，失败时可安全重试。
7. 客户详情显示合同、应收、租户和权益的关联状态；所有步骤保留审计事件。

### 7.2 续约、升级和到期

1. 总览展示临期合同和权益；运营人员从原客户/合同发起续约。
2. 续约生成新合同版本/条目并保留旧合同历史，明确新期限、价格和权益差异。
3. 收款按新付款计划登记；符合合同条件后提交授权延期/变更申请。
4. 审核后通过幂等 API 同步租户权益；失败状态进入交付待办。
5. 到期时先提醒和标记到期；任何暂停动作需权限和明确理由，不物理删除租户或商业记录。

### 7.3 私有化交付和售后

1. 合同选择私有化销售方式并形成授权快照。
2. 交付运营创建部署实例，登记授权和当前软件版本；实际安装在外部流程完成人工执行。
3. 售后工单可关联部署实例、合同或授权；版本升级登记只记录已执行的结果。
4. 维护到期和长期未升级实例进入总览提醒；后台不存放远程登录凭据。

## 8. 状态规则

| 对象 | 状态/派生值 | 规则 |
|---|---|---|
| 客户 | signed / onboarding / active / suspended / terminated | 表示商业服务关系，不替代合同、账款和租户状态 |
| 合同 | draft / reviewing / signed / active / expired / terminated | 生效后的核心内容通过新版本/变更记录调整 |
| 应收 | upcoming / unpaid / partial / paid / overdue / reversed | 根据计划日期、核销余额和独立冲销流水计算 |
| 收款 | recorded / pending_reconcile / reconciled / reversed / refunded | 原记录不覆盖，撤销和退款以反向事实表示 |
| SaaS 订阅/授权 | draft / pending_approval / active / suspended / expired / revoked | 权益变化必须通过审核命令并留下版本历史 |
| 租户同步任务 | pending / succeeded / failed / retrying / cancelled | 幂等键确保重试不会重复应用副作用 |
| 私有化实例 | planned / active / maintenance / retired | 环境状态不自动改变合同或授权状态 |
| 售后工单 | new / assigned / in_progress / waiting / resolved / closed | 状态变更进入不可覆盖的处理时间线 |

不同状态实体独立维护；禁止以一个通用 `status` 字段混合合同、付款、授权、租户和部署状态。

## 9. 数据与接口边界

### 9.1 逻辑数据域

运营后台拥有客户关系、联系人、产品/套餐、价格版本、合同及条目、应收与收款流水、订阅/授权快照、部署台账、售后工单、运营账号授权、审计和集成任务等逻辑数据。

`udone` 拥有旅行社组织/租户内部用户及所有旅行社业务数据。运营后台只保存关联 ID 与必要的状态摘要，不复制其业务明细。

### 9.2 数据库与访问

- 同一 Supabase 项目中使用运营专属 schema 和表；本文以 `ops` 作为逻辑代称，确切 schema 名在技术规格中统一。
- `ops` 数据通过受控 Hono API 访问；浏览器不得携带 service role，也不得通过随意暴露的数据库表绕开业务命令。
- 如开放 Supabase Data API 自定义 schema，必须显式配置暴露清单、Postgres grants 和每张表 RLS；默认优先只暴露 API 需要的最小对象。
- RLS 使用服务端维护的运营成员关系/可信 JWT 声明，不信任用户可编辑资料字段；每张暴露表明确读写策略。
- 合同、应收、收款、核销、退款、授权和租户命令的跨表写入须由事务/RPC 或等价原子业务操作保证一致性。
- 以迁移文件作为数据库结构真源；PRD 不定义具体表名、索引 SQL、RPC 参数和 API JSON 字段。

### 9.3 Hono API 边界

- 运营接口位于独立版本化命名空间（建议 `/api/v1/ops/*`）；`udone` 租户侧接收运营交付命令使用显式内部接口。
- API 先验证身份，再验证运营账号状态/角色/权限，最后执行输入校验、业务规则和数据访问。
- 领域模块之间通过服务/用例接口协作，路由层不直接编排跨域 SQL。
- 集成命令使用版本号、幂等键和关联业务 ID；返回可查询的命令状态，而不是只返回一个不可追踪的超时错误。
- API 契约和错误码在实现前形成单一共享规范；不得从界面内容猜测 `udone` 的表或字段。

## 10. 非功能要求

### 10.1 性能基线（首轮验收目标）

下列为规划验收基线，不代表已完成压测：

- 普通列表在 10,000 个客户档案、100,000 条合同/账款/工单记录的合成数据下，服务端筛选分页的 p95 响应时间不超过 800 ms（不含公网网络和外部 `udone` 调用）。
- 运营总览汇总 p95 不超过 1.5 s；页面不一次性下载全部明细后在浏览器聚合。
- 常规写入 p95 不超过 1 s；外部租户操作按异步命令状态返回，不阻塞页面请求等待外部系统完成。
- 默认分页大小不超过 50 行；大规模导出使用受权限控制的后台任务，避免请求超时。
- 关键查询按客户、合同、状态、到期时间和关联对象建立适当索引；不得对列表每行触发重复查询。
- 性能验收在约定的测试环境、数据规模和并发下执行并记录，单个目标未达标须定位是查询、网络、外部 API 或 Worker 资源所致。

### 10.2 安全与隐私

- 所有页面和 API 强制 HTTPS；密钥只存在 Worker secrets 或等价服务端密钥管理中。
- `ops` 与旅行社租户授权域分开；匿名用户和普通 `udone` 用户访问运营 API 必须被拒绝。
- RLS 与 API 权限双重执行；所有暴露表默认拒绝，逐条授予最小权限。
- 运营账号邀请/重置由管理员控制；首期运营登录至少支持强密码策略，并按 Supabase 当前能力启用 MFA/高风险二次验证。
- 个人联系方式按角色最小化展示；下载、收款、退款、授权和批量导出写入审计。
- 运维日志脱敏，不含密码、Cookie、Authorization、完整支付卡信息、私有化环境秘密或不必要的客户个人数据。

### 10.3 可靠性与一致性

- 金额使用精确十进制类型，禁止浮点金额计算；服务端根据明细复算总额。
- 账款、退款、权益和状态变更采用不可覆盖流水/事件；更正通过冲正或新版本完成。
- 幂等键在数据库有唯一约束；API 重试返回同一业务结果或明确冲突。
- `udone` 同步失败不得把运营状态标成已成功；提供重试上限、退避和永久错误分类。
- 重要操作失败可定位到请求 ID、关联合同/客户和安全摘要，且可由有权限人员恢复。

### 10.4 可维护性与模块化

- 前端按页面域组织为客户、产品、合同/账款、授权/租户、私有部署、售后、审计等功能模块；公共组件只承载稳定跨域能力。
- 后端逻辑按 customer、catalog、contract、billing、entitlement、tenant-integration、deployment、support、identity/audit 领域组织；不得创建重复的跨模块 CRUD。
- 领域规则位于服务层/事务边界，不散落在页面和 HTTP 路由中。
- 继续使用 `udone` 的单 Hono Worker 部署；只有可度量的独立扩缩容、安全或故障隔离需求出现后才重新评估服务拆分。
- 数据库 migration、角色/权限数据和 API 契约可在新环境可重复部署；工程约束另由项目 `.harness` 文档维护。

## 11. 验收标准

### 11.1 核心流程验收

1. **运营身份**：普通旅行社用户、匿名用户和停用运营账号均不能读取或写入运营数据；已授权角色只能执行被授予动作。
2. **客户与合同**：同一客户可关联多份合同；客户/合同重复编号被拒绝；生效合同修改产生新版本或变更历史，旧内容可查。
3. **商品权益快照**：新套餐价格/权益变化不改变历史合同与已生效权益。
4. **线下收款**：可创建多期应收、分次收款、跨应收分配；并发核销不会超额；退款和冲正不覆盖原记录。
5. **租户开通**：审核前不允许执行；审核后通过 API 创建或绑定租户；同一命令连续重试只产生一个结果；失败能看到原因类别并安全重试。
6. **权限隔离**：运营角色不能直接访问旅行社业务明细；`udone` 普通用户不能访问运营 schema/API；未授权写入由 API 与 RLS 阻止。
7. **私有化交付**：能够登记客户部署、授权、当前版本和升级历史；系统不会保存远程登录秘密，也不宣称完成自动部署。
8. **售后工单**：可创建、分派、等待、解决、关闭和重开；每次变化均保留时间线；可按客户/租户/部署追溯。
9. **审计**：对合同生效、收款核销、退款、授权发放/停用、租户操作、角色变更和导出均能查到操作者、时间、对象、原因及请求关联 ID。
10. **总览口径**：指标与对应筛选明细一致；逾期、到期、未核销和同步失败定义明确；权限受限用户只看到授权范围。
11. **性能**：在 10.1 指定合成数据规模下达到性能基线并保存测试报告。
12. **部署**：前端使用 Vben `web-antd` 作为起始模板；前端部署可单独发布，后台 API仍由 `udone` 的 Hono Worker 提供；不得在前端包中包含 service role 或第三方私密密钥。

### 11.2 首期交付完成定义

- 本 PRD 覆盖的 P0 流程均有页面、API、迁移、RLS、审计和自动化验收。
- 运营用户/角色授权矩阵、`ops` 与 `udone` 数据边界、租户同步契约可追溯到技术设计文档。
- 使用纯虚构客户、合同、账款和工单数据完成端到端验收。
- 性能、安全、RLS 跨域拒绝、幂等重试均有可复核结果。
- 不存在绕过审批直接发放权益、从客户端修改财务/授权核心状态或用 UI 隐藏替代授权检查的路径。

## 12. 运营报表和指标口径

| 指标 | 口径 |
|---|---|
| 有效软件客户 | 客户状态为 active，且至少一个合同/权益仍有效；客户暂停另行呈现 |
| SaaS 运行租户 | 最近一次 `udone` 同步状态为成功且运行态为 active 的唯一租户映射数 |
| 合同待收金额 | 已签/生效合同应收计划余额；未签合同不计入 |
| 逾期应收金额 | 到期日早于统计日且仍有未核销余额；退款/冲正按独立流水扣减 |
| 临期权益 | 未来配置窗口内到期的有效订阅/授权，不含已撤销对象 |
| 开放工单 | 状态不为 resolved/closed 的工单数，等待状态单独分组 |
| 租户同步失败 | 最新命令状态为 failed，且尚无成功重试的唯一商业操作数 |
| 私有部署版本分布 | 以当前有效部署实例的最近一次确认版本统计；缺少版本单独列为未知 |

统计须注明数据更新时间、时间区间、币种口径和过滤状态；看板与明细导出复用同一口径服务。

## 13. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 运营角色误获旅行社权限或反向越权 | 运营账号池、角色域、API 命名空间、schema 和 RLS 分隔；建立正向/反向拒绝验收 |
| 共享 Supabase Auth 被误解为完全隔离认证 | PRD 明确只是逻辑身份域分开；不提供独立用户存储保证；保留认证适配层和迁移步骤 |
| 运营客户与 `udone` 组织重复或错绑 | 使用稳定外部 ID 映射，数据库唯一约束、预览确认、幂等 API、冲突拒绝 |
| 合同/收款状态与租户权益不一致 | 商业状态和运行状态分开；每次变更通过可追踪命令同步，失败进入待办，不虚报成功 |
| 产品改价影响历史合同 | 合同条目和权益使用不可变快照；目录新版本仅用于未来合同 |
| 同步超时导致重复开通/扣减 | 幂等键、命令查询、事务约束和冲突处理；超时不盲目重试 |
| 私有化运维秘密泄露 | 仅记录环境标识和运行元数据，不存远程凭证，不提供远程命令执行 |
| 共享后端形成性能热点 | 列表服务端分页、关键索引、聚合读模型、后台导出；按基线压测并观察 Worker/DB 资源 |
