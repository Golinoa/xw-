## 本地数据库验证环境（udone）

`pnpm db:local:verify` = 起临时 PostgreSQL 17 → 空库重放全部迁移 → 跑 pgTAP → 停库。
二进制与 pgTAP 装在仓库外 `$HOME/.udone-local-pg`，不动工作区。

**踩过的坑（脚本注释里有详细说明，别再重犯）**
- 不要用 `pg_ctl start`：postmaster 会脱离终端，被 shell 收尾时一起杀掉。用子进程 + `pg_ctl stop`。
- 不要 `process.exit()`：管道 stdout 是异步写，日志会被整段吞掉。用 `process.exitCode`。
- pgTAP 必须 `psql -t -A`；默认表格格式下 `^ok` 一条都匹配不上，失败会被当成「0 断言通过」。
- pgTAP 消息正则用 `throws_like`，`throws_ok` 是精确比对。

**测试真的抓到两个生产级缺陷**
- 建单/改单/状态机全是 500：事务函数 SECURITY INVOKER，而 `authenticated` 只有 SELECT，
  且列级 UPDATE 漏了 `status/previous_status/customer_id/order_type`。已按列补齐授权。
- 软删除的行在 RLS 层仍可读（API 靠 `deleted_at=is.null` 过滤）。已在策略层收紧，
  并改掉 API 软删除对 `return=representation` 的依赖。

**未修的已知缺陷（最优先）**
`update_order_with_items` 整体替换明细行，导致 `confirmed_amount/pending_amount` 归零——
改线路名会抹掉已确认收款。需要契约带上明细行 id 才能修。

## 订单编辑：金额行按 id 增量合并（修掉丢钱缺陷）

`update_order_with_items` 原本删光明细再插入，`confirmed_amount` 归零——
改个线路名就抹掉客户已确认的 3000 元。已改为按 id 合并：带 id 原地更新、
不带 id 新增、请求里缺席的才删。

**三条前置判定（都在写入之前返回）**
- `LINE_NOT_FOUND`：行 id 不属于本订单（用 text 比较，非法 uuid 不会抛 22P02 变 500）
- `LINE_AMOUNT_CONFLICT`：新金额 < 已确认 + 在途
- `LINE_HAS_PAYMENTS`：有收付款的行不能删

**踩过的坑**
- `array_agg` 会保留重复，拿它跟「带 id 的行数」比对做重复检测永远相等 → 必须 `DISTINCT`
- 列级 UPDATE 授权一直缺席，`order_receivables_update_writer` 策略写了却从没生效过；
  补 `GRANT UPDATE (name, amount, updated_at)`，`confirmed_amount/pending_amount` 仍不开放
- pgTAP 里 `create_order_with_items` 自己生成订单 id，断言不能写死 id；
  真实 id 存进事务级 GUC（`set_config('test.main_order', ...)`）再引用

**验证**：`db:local:verify` 11 迁移 + 8 文件 130 断言；单测 34 文件 197 用例；
format/lint/schema/deploy/typecheck/build 全绿。

**仍未修**：明细行写入策略不看父订单状态，completed/cancelled 的订单行仍可被
直连 PostgREST 增删改（API 层已挡）；这是本次之前就存在的口子。

## 明细行状态守卫 + 收付款申请

**迁移 07**：明细表 insert/update/delete 六条策略加 `parent_order.status IN ('booking','active')`。
`lock` 就是 active→completed，没有独立锁定列，所以「可写」= 业务进行中。
变异验证：去掉条件后 4 条断言（completed 增改删 + cancelled 增）同时红。

**迁移 08**：`finance_applications`（收付共用一张表，kind + 两个可空外键 + CHECK 互斥）
+ `finance_application_actions`（只追加的审批轨迹）；四个函数 + 三个额度调整辅助函数。
不变式：pending 占用额度不计收入，终审才进 confirmed；驳回/撤销释放；终审撤回退回在途。

**踩过的坑**
- `REVOKE ... FROM public.authenticated` 是语法错误，`authenticated` 不是 public 模式下的对象
- plpgsql 引用后置定义的函数不报错（延迟解析），只有执行才炸 → 只能靠测试抓
- UUID 前缀必须是十六进制，`h` 非法（c/d/e/f 都是合法 hex，所以之前没踩到）
- 额度调整函数**必须 REVOKE FROM PUBLIC**：PostgreSQL 默认给 PUBLIC 授 EXECUTE，
  不显式收回等于把 confirmed_amount 的任意写开放给客户端
- 测试计数出现过 193/195/197 三种结果，随后连跑三次稳定 197；疑似与并行跑其他门禁抢 CPU 有关，
  无证据。门禁改为顺序执行。

**当前规模**：13 迁移、10 个 pgTAP 文件 161 断言、34 个单测文件 197 用例。

result_application_id / new_status / new_step / error_code 四组列名、业务失败走返回值而非异常。

**前端**：`/finance/applications` 待审列表（URL 即状态）+ 审批/驳回/撤回/撤销 + 发起入口挂在订单金额行上。

变异验证：把付款分支 pending 改成 confirmed，第 2/3/10 条变红，随后 CHECK 约束也让文件执行报错。
