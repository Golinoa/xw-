## 二、本机三个坑（都已解决，记录以免重犯）

1. **`NODE_OPTIONS` 注入了安全删除钩子**
   环境里有 `--require=genie-safe-delete.cjs`，它把 Node 的所有删除改写成「进回收站」，
   而本机回收站 API 是坏的（`Some operations were aborted`）。
   ⇒ 任何会删文件的 Node 命令（`pnpm install` / `pnpm typecheck` / 脚本）都要 `env -u NODE_OPTIONS` 前缀。

2. **`api.github.com` 被限流 403**
   `local-db.mjs` 用 GitHub API 找 PostgREST 最新资产会挂。绕过：直接下 v16.5 直链。
   pgTAP 则用 `codeload.github.com` 的 tag 包（`fetch failed` 时 curl 能过）。

3. **Git Bash 的 `tar` 不认 zip**
   用 `/c/Windows/System32/tar.exe`，且必须传 Windows 路径（`cygpath -w`）。

## 四、卡在哪 & 怎么继续（2026-11-15 02:5x 更新）

依赖装不上，**不是网络、不是版本、也不是删除保护**。挖到最后是两个具体原因叠加：

### 原因 A：每次被终止的 pnpm 都留下 2 个孤儿进程，占住 store 的 SQLite 锁

`ps` 里看不到（它们挂在 Windows PID 上），但 `Win32_Process` 一查就是 10 个：
`pnpm.mjs install --frozen-lockfile ...` 挂着不动，全部等 `D:\.pnpm-store\v11\index.db` 的写锁。

表现：**安装永远停在「added 17 / 41 / 45 / 70」某个数字上不动，日志十分钟不写一行。**
更坑的是：下一次安装也会被这些孤儿挡住，所以越重试越像「环境坏了」。

清理办法（每次中断后必做）：

```powershell
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.CommandLine -like '*pnpm*' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
Remove-Item 'D:\.pnpm-store\v11\index.db-shm','D:\.pnpm-store\v11\index.db-wal' -Force
```

### 原因 B（2026-11-15 13:50 更正）：不是「写入被拦」，是 **下载超时**

之前的判断是「大 tarball 写入失败」，**错了**。用户在沙箱外跑了两次同样失败，
逼着去实测，才看清真相：

| 实测项 | 结果 |
| --- | --- |
| 本机到 registry 的下载速度 | **约 640 KB/s**（npmmirror CDN 677 KB/s、npmjs 604 KB/s，两者都能下） |
| `@cloudflare/workerd-windows-64` 体积 | **34.5 MB**，单独下要 **54 秒** |
| pnpm 默认单项超时 | **60 秒** |
| pnpm 默认并发 | **16 路** |

三项一乘就明白了：

1. 34.5 MB 的包在 640 KB/s 下要 54 秒，**离 60 秒的默认超时只差 6 秒**；
2. 16 路并发把带宽切碎，每个流只剩约 40 KB/s —— `@esbuild/win32-x64`（约 10 MB）
   需要 250 秒，`typescript`（4.3 MB）、`prettier`、`playwright-core`、`miniflare` 同理；
3. 于是**所有大包在 60 秒被掐**，报 `error (23)` / `TimeoutError: The operation was aborted due to timeout`。

这也解释了为什么失败的永远是同一批包（`@esbuild/win32-x64`、`workerd`、`typescript`、
`prettier`、`playwright-core`、`miniflare`）—— 它们正好是体积最大的那几个，小包从不失败。
换源当然无效：两个源速度一样，问题不在源。

**修复**（已写进脚本）：

```
--fetch-timeout=600000        超时 10 分钟
--network-concurrency=4       并发降到 4（每流带宽回到 160 KB/s 左右）
--fetch-retries=5             失败重试 5 次
--fetch-retry-maxtimeout=60000
```

外加「最多 3 轮」重试循环：store 是累积的，每轮会接着上一轮的进度，所以失败重跑不会从零开始。

⚠️ 注意 `--config.network-concurrency=4` **不能用**：它会被解析成两级配置
（`network.concurrency`），报 ``Expected `concurrency` to be a number from 1 and up, got `4` (string)``。
必须用显式的 `--network-concurrency=4`。

### 结论

在普通终端（或双击 `一键启动本地环境.bat`）跑即可，**不需要绕开什么**。

```powershell
powershell -ExecutionPolicy Bypass -File D:\Coding\ERP\.workbuddy\tools\bootstrap-udone-env.ps1
```

预期：`db:local:http` 起 PG + PostgREST + 存储替身，跑 21 个 HTTP 集成用例。

**当前本机残留**（句柄未释放，删不掉，重启后可清）：
`udone/node_modules`（半成品）、`.verify-deps/`、`udone/apps/api/.nm-bad/`、`udone/apps/web/.nm-bad/`。
仓库 tracked 文件没有改动，`git status` 只有 `.workbuddy/` 与 `admin/.superpowers/`。

## 六、一键脚本（已实测）

### 双击入口

**`D:\Coding\ERP\一键启动本地环境.bat`** —— 在资源管理器里双击即可，不用开终端。

- 双击后弹出一个控制台窗口，标题 `ERP local environment bootstrap`；
- 默认带 `-Fresh`：先删半成品 `node_modules` 再装，等于自我修复；
- 跑完会停住并显示退出码，按任意键关闭（不闪退）；
- 只想起数据库、不装依赖：先设环境变量 `ERP_SKIP_INSTALL=1` 再双击。

`.bat` 本身只有二十来行、纯 ASCII（中文注释在 GBK 控制台下会让 cmd 解析错位），
逻辑全在 `.ps1` 里。这个文件已加入 `.git/info/exclude`，不进仓库。

**双击链路里我无法亲自验证的部分**：`cmd.exe` 在本机被安全策略拦住，我只能验证
它调用的 `.ps1`（`-SkipInstall` 全跑通：40 迁移 / 32 测试文件全绿）。
`.bat` 用到的 `%~dp0`、参数透传、退出码回显都是标准写法；首次双击若报错，
把窗口里第一条错误行发我即可。

### 脚本本体

`.workbuddy/tools/bootstrap-udone-env.ps1` —— 把上面所有手工步骤串起来：

| 步骤 | 内容 |
| --- | --- |
| 1 | 结束残留的 `pnpm.mjs` 孤儿进程（清锁的前提） |
| 2 | 删 `index.db-shm` / `index.db-wal`，删不掉只告警不中断 |
| 3 | 清空 `NODE_OPTIONS`、设 `CI=true`；并检查 `pnpm` / `node` 在 PATH 上（双击时环境和终端不同） |
| 4 | `-Fresh` 时用 `cmd rmdir` 删半成品 `node_modules`（PowerShell 删不掉断链 junction） |
| 5 | `pnpm install --frozen-lockfile` |
| 6 | `node scripts/db/local-db.mjs verify` |
| 7 | `node scripts/db/local-db.mjs http` |

**实测记录（2026-11-15 13:31，`-SkipInstall -SkipHttp` 模式）**：

```
=== 清理残留的 pnpm 进程 ===   OK  没有残留进程
=== 清理 pnpm store 的 SQLite 热日志 ===   OK  锁已清空
=== 清理环境变量 ===   OK  NODE_OPTIONS 已清空、CI=true
=== 重放迁移 + pgTAP（约 1 分钟） ===
PostgreSQL 已启动：127.0.0.1:55432
迁移重放通过：40 个文件，库 udone_local
全部通过：32 个测试文件
PostgreSQL 已停止
  OK  数据库层全绿
```

退出码 0，耗时 61 秒。**说明脚本的第 1~3、6 步是对的**；
第 4/5/7 步（删 node_modules、装依赖、跑 HTTP 集成）只能在沙箱外验证，我这边无法执行。

脚本里的两个坑（已修，记下来省得重踩）：

1. **必须以 UTF-8 with BOM 保存**。PowerShell 5.1 按系统 ANSI 读 `.ps1`，无 BOM 时中文注释会让解析错位，
   报「表达式或语句中包含意外的标记 `}`」，而且报错行号指向字符串之外，很难看出来。
2. **`catch {}` 空块在 5.1 里不接受**，改成 `-ErrorAction SilentlyContinue`；
   另外 `[Console]::OutputEncoding = UTF8` 必须设，否则 node 的中文输出会变成 `宸插惎鍔?` 这种乱码。

## 五、这套环境的边界

能干的：前端 46 条联调、双身份权限判定、拒绝路径、部署脚本走通、contract 对齐。
不能干的：性能基线（同机跑 DB 与前端，CPU 争用）、恢复演练（无独立存储）、
以及任何「与生产等价」的结论 —— 同机 ≠ staging。

`.env` 目前没建（`pnpm db:local:*` 自带注入，不需要）。等前端要连本地后端时再按 `.env.example` 补。
