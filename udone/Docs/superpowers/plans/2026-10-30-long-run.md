# 长任务持续推进计划（2026-10-30 起）

> **一句话结论：** 40 张待办里 **39 张**归我（`a-opsfix` 是运营端回写契约正文的活）。它们不是 39 个独立任务，而是**一条串行主线 + 一条可并行的填缝线**：主线的 8 个业务域之间是链式依赖（客户→合同→应收→收款→权益），拆不开；填缝线与主线零交叉，所以现在做只会推迟里程碑，不会加快任何东西。计划把这 39 张切成 **约 70 个推进单元**，每单元一刀一提交、出口可观测、失败即停，靠固定的断点协议跨工作段接力。
>
> **读者边界：** 本文件只排**顺序、切法与验收口径**，不重定义契约。ops 的字段/端点/错误码真源仍是 `admin/Docs/ops-api-contract.md`，差异裁决见 `2026-10-30-ops-alignment.md`，域级步骤见 `2026-10-30-ops-backend-implementation.md`。三者冲突时：契约 > 差异台账 > 本文件 > 实施计划。

## 2. 主线判定：为什么是这个顺序

三条候选线的对比：

| 线 | 外部等待方 | 内部依赖 | 现在做的收益 | 裁决 |
|---|---|---|---|---|
| **ops 主线** | 有（运营端 9 域全在桩上，399 个单测无从验证） | 强串行 | 每交付一个域，对方能关掉一片桩 | **主线** |
| 业务 backlog | 无 | 弱（`c1`~`c12` 相互独立） | 自查式完善 | 填缝 |
| 工程债 | 无 | 无 | 降低后续成本 | 见 §2.2 两个例外 |

### 2.1 ops 为什么不能并行推进

11 个域不是并列的 11 个模块，而是**一条数据链**：

```
身份基座 ──┬─→ 客户 ──→ 合同 ──→ 应收 ──→ 收款 ──→ 权益
           └─→ 产品 ──↗                          ↘ 租户映射
                                        工单 / 报表 读全部前三层
```

`o-t06`（合同）要引用客户与套餐；`o-t07`（应收）的计划合计必须等于合同金额；`o-t08`（收款）的核销上限由 SQL 聚合判定；`o-t13`（报表）口径横跨合同/应收/收款。**跨层并行会造出假的类型与假的断言**——下层形状没定就写上层，测试只能对 mock 断言，等于把桩的问题搬进后端。

### 2.2 两个必须提前的例外

| 卡 | 为什么不能等到最后 |
|---|---|
| `a-deps`（critical 2 / high 20） | `o-t08` 是唯一写钱的域（核销、冲正、退款）。带已知 critical 依赖写资金逻辑，等于把风险埋在不可回滚的路径上。**`o-t08` 开工前必须清完 critical** |
| `d1`（主 chunk 1,638 kB） | 每加一个域 chunk 只增不减。现在拆是按模块边界拆，等 11 个域都进来就是按「已成型依赖链」拆，成本高一个量级 |

其余 16 张（`a1` `a5` `d2` `b1` `b2` `c1`~`c12`）排到主线走完 8 个域之后。**理由不是不重要，是没有等待方**：它们推迟一段，损失为零；`o-t04` 推迟一段，运营端那一域继续在桩上，损失是一整片无法验证的功能。

### 2.3 一处顺序纠正（相对旧计划）

`o-cors` 与 `o-testjwt` 原本包在 `o-w04` 里。现在拆出来独立做，因为二者**都不依赖 `ops.operators` 表**，可以在身份基座之后、`/meta` 之前并行收口；而登录代理必须等 CORS 通了才有意义（cookie 跨源丢不丢是登录能不能用的前提）。顺序改为：

```
U01 身份基座 → U02 /meta → U03 CORS → U04 测试签发 → U05 登录 → U06 /session
```

比旧顺序多一步，但 CORS 的红会早两个单元暴露。

## 3. 推进单元（Unit）：长任务的真正单位

**任务卡是「目标」，单元是「一刀」。** 一张卡可能 1 刀（`d1`）也可能 6 刀（`o-t08`）。切分的唯一标准：**这一刀能否独立提交并通过全部 11 道门禁**。

### 3.1 单元固定五步

| 步 | 动作 | 不通过怎么办 |
|---|---|---|
| 1 入口 | 读最近一份 journal 的 `## 断点` 段；`pnpm board:check`；`git status` 干净 | 断点缺失 → 先补，不动代码 |
| 2 实施 | 只碰本单元声明的文件（写在 §4 表里） | 发现要碰表外文件 → 说明切分错了，回 §4 重切 |
| 3 单元验证 | pgTAP 或（单测 + 集成），只跑本单元的 | 红 → 改实现，不改断言（除非断言本身写错，需在提交信息里说明） |
| 4 门禁 | 11 道全量（见 §3.2） | 红 → 定位；定位不了就回退到单元入口 |
| 5 收口 | 1 个提交 → 看板状态 + **实测**数字 → journal 追加 `## 断点` | 三者缺一不算收口 |

### 3.2 11 道门禁（当次实测，不许引用历史）

```
pnpm board:check && pnpm format:check && pnpm format:sql:check && pnpm lint \
  && pnpm schema:check && pnpm check:deploy && pnpm typecheck && pnpm test \
  && pnpm build && pnpm db:local:verify && pnpm db:local:http
```

### 3.3 业务域的同构切法（这是能持续的关键）

11 个业务域全部按同一个四刀切，不要每域另设计一套：

| 刀 | 产物 | 出口断言 |
|---|---|---|
| **S1 schema** | 1 个迁移（表 + 索引 + RLS + 必要 RPC）+ 1 个 pgTAP 文件 | P1 `anon` 无 USAGE；P2 租户成员查该域表 0 行；P3 越权插入被 `WITH CHECK` 拒；P4 `invited`/`disabled` 0 行；函数 `search_path=''` 且未授 `public`/`anon` |
| **S2 契约** | `packages/contracts/src/ops/<domain>.ts` + `OPS_ROUTES` 登记 + 请求/响应 zod | `parity` 绿（登记 ↔ 挂载一一对应）；类型层编译过；无 `as any` |
| **S3 端点** | `apps/api/src/modules/ops/<domain>/` + 单测 + 集成 | 真实 PostgREST 下每端点至少 1 条 2xx + 1 条拒绝；`respond()` fail-closed 生效 |
| **S4 拒绝证明** | 该域相关的 P5~P13 子集 | 该域写进 §4 表的那几条，逐条有断言 |

**为什么切四刀而不是一把做完：** 一把做完的单元如果第 3 步红，你无法判断是 schema 错、契约错还是端点错，只能整块回退。四刀每刀失败面小，且 S1 绿之后 S2/S3 可以不同工作段做——**这是一条 70 单元的路能跨会话跑完的前提**。

## 6. 检查点（每段末，不是每单元）

| 项 | 要求 |
|---|---|
| 11 道门禁 | 全量跑，数字抄输出，不抄记忆 |
| 变异验证 | **抽 1 条**本段新增的关键断言，故意改坏实现，确认它变红。没红的断言等于没写 |
| 看板 | 每张卡移状态 + 写实测数字 + 提交哈希；`pnpm board:check` 绿 |
| journal | 追加 `## 断点`（见 §8） |
| 四态 | 对外汇报按「已交付已验证 / 已交付未验证 / 进行中 / 未开始」逐项，不许合并 |

变异抽查为什么必须有：这一轮已经踩过两次「测试全绿但没测到东西」——`vitest` fork worker 静默失败吞掉 15 条断言仍报 38 文件全过；幂等第一枪变异返回数组导致缓存失效反而没测到命名空间。**绿不是证据，「改坏它会红」才是。**

## 7. 止损规则

| 情形 | 处理 |
|---|---|
| 同一单元门禁红 3 次 | 停。写问题登记（现象/已排除/下一步假设），转下一单元，不硬推 |
| 门禁红且一段内定位不了 | 回退到单元入口（`git checkout` 本单元文件），不留半成品 |
| 发现契约与实现冲突 | 记 DIF 台账，**不改对方契约正文**；自己按契约实现，冲突写进 handoff |
| 发现单元要碰表外文件 | 说明切分错了 → 回 §4 重切，不硬扩边界 |
| 单段超过 3 个单元未收口 | 说明粒度还是太大 → 再切一刀 |

「不留半成品」是硬约束：**长任务最容易死在「一堆做到 80% 的单元」上**，那状态既不能提交也不能丢弃。

## 8. 断点恢复协议（跨工作段接力）

journal 每单元末尾固定追加，格式不可变：

```markdown
## 断点（YYYY-MM-DD HH:MM）
- 本单元：U05 / o-w04 登录代理
- 已完成：CORS 三断言绿；jwt 签发通道可用
- 未完成：refresh 轮换未接
- 下一单元：U05 续（refresh + 429）
- 阻塞：无
- 环境：迁移 17 个；pgTAP 12 文件 214 断言
```

下一段开工第一件事是读它，不是读对话。**对话会被压缩，journal 不会。** 这条是我这轮的实际教训——跨段接手时最贵的不是写代码，是重建「我上次做到哪、为什么停」。
