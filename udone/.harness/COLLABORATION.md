# 双端协作约束

跨端协作最贵的不是写代码，是**同一件事被反复提起、每次状态都靠记忆**。这一份规定「需要运营端配合的事」怎么记、怎么推进、什么时候算闭环。

数据在 `XW-ERP/dev-board.html` 的 `COLLAB` 常量，展示在看板「🤝 双端协作」页，`pnpm board:check` 校验。三者是同一份数据的三个视角，不是三个副本。

## 0. 术语口径：只说「业务端」和「运营端」

| 称呼 | 指什么 | 位置 |
|---|---|---|
| **业务端** | 本仓库，ops 后端的实现方 | `D:/MYC/Coding/ERP/udone`，分支 `feat/business-slice` |
| **运营端** | 相邻工作副本，运营控制台与其契约真源 | `D:/MYC/Coding/ERP-ops`，分支 `feat/ops-console` |
| 两端 | 只在确实指双方共同行为时使用 | — |

**禁用第一人称与泛指**：我 / 我们 / 我方 / 我这侧 / 对方 / 他们 / 对端。

理由有两条，都不是文风洁癖：

1. **这份文档的读者就是运营端。** 写给运营端看的文件里写「我方要做什么」，运营端读到的是「运营端要做什么」——指代正好反过来。一次误读的代价是照着错的角色去干活。
2. **「对方」把工程问题降格成私人往来。** 谁欠谁一件事、谁先松的口，这类判断一旦进入文档，状态就从事实变成印象。写「运营端未回写契约 §5.1」可以核对，写「他们还没理我们」不能核对。

`board:check` 会拦 `COLLAB` 里的这七个词，违反即红。**检查失败改措辞，不改脚本。**

## 1. 唯一登记处

「需要运营端配合」只能记在 `COLLAB` 里。禁令：

- 不写在任务卡的 desc 里（卡是「业务端要做什么」，不是「运营端欠什么」）
- 不写在 journal 里当唯一记录（journal 是时间线，会被后一条覆盖语义）
- 不写在对话里（对话会被压缩）

一本账。否则「这件事到底提过没有、运营端回没回」就要翻三个地方。

## 2. 每条必须包含五件事

| 字段 | 要求 | 反例 |
|---|---|---|
| `impact` | 说不做会怎样，要具体到后果 | 「影响联调」 |
| `need` | **要运营端做什么**，可以照做的动作 | 「沟通一下」「对齐一下」「同步一下」 |
| `due` | 何时需要（段号或里程碑） | 「尽快」 |
| `blocks` | 看板任务 id，被卡住的那几张 | 无，或写卡标题 |
| `evidence` | 依据：契约章节、行号、或运营端提交 | 「之前说过」 |

`need` 的写法标准只有一条：**运营端看完可以直接动手，不需要再问业务端一句「你具体要什么」**。写不成这样就说明事情还没想清楚，不该登记。

`blocks` 必须是真实存在的任务 id。它存在的意义是让「哪张卡被哪件事卡住」可查，而不是靠读描述猜——`board:check` 会校验 id 存在，且**未闭环的协作项不许阻塞一张已 done 的卡**（那说明状态自相矛盾）。

## 3. 四态

| 状态 | 含义 | 谁能推进到下一态 |
|---|---|---|
| `blocking` | 卡业务端开工，没有它这条线动不了 | 运营端回复后转 `answered` |
| `waiting` | 等运营端回，但不卡当前单元 | 运营端回复后转 `answered` |
| `answered` | 已回，待业务端落地实现 | 业务端实现并验证后转 `closed` |
| `closed` | 已闭环 | — |

`closed` **必须能定位**：提交哈希、`§章节号`、或具体行号，三者至少一个。

这条被变异测试打过一次：第一版写的是「证据里含『已』字」，结果任何中文句子都能过，等于没检查。**闭环不能靠语气词证明。**

## 4. 业务端不替运营端改契约

契约真源在运营端仓库（`admin/Docs/ops-api-contract.md`）。发现缺口：

1. 记一条 `COLLAB`，`type` 写「裁决」或「回写」，`need` 写明业务端需要的结论
2. 业务端按**当前契约**实现，不按「应该是」的样子
3. 同时在 `2026-10-30-ops-alignment.md` 记 DIF 编号
4. 运营端改了正文 → 业务端复核行号 → 转 `closed`

**不直接在运营端文件里改**。改了就没人知道那是谁的决定，下次漂移时也找不到源头。

## 5. 推进时机

- **每段开工**：先扫 `blocking` 项。有就说明这段不该开工，去催或改计划。
- **每段收口**：检查本段是否产生新的 `answered`（运营端回了但业务端没落地）——这类最容易被忘。
- **里程碑节点**：`due` 与本段相关的项，逐条给四态，不许合并成一句「在等运营端」。

## 6. 检查

```bash
pnpm board:check
```

校验：id 唯一 · 状态与类型合法 · 五字段齐全 · `need` 不是空话 · `blocks` 指向真实任务且不与 done 冲突 · `closed` 可定位 · 无第一人称/泛指。

检查失败**改数据，不改脚本**——放宽检查等于把这一页重新变成装饰。
