# 双端协作约束

跨端协作最贵的不是写代码，是**同一件事被反复提起、每次状态都靠记忆**。这一份规定「需要对方配合的事」怎么记、怎么推进、什么时候算闭环。

数据在 `XW-ERP/dev-board.html` 的 `COLLAB` 常量，展示在看板「🤝 双端协作」页，`pnpm board:check` 校验。三者是同一份数据的三个视角，不是三个副本。

## 1. 唯一登记处

「需要对方配合」只能记在 `COLLAB` 里。禁令：

- 不写在任务卡的 desc 里（卡是「我方要做什么」，不是「对方欠我什么」）
- 不写在 journal 里当唯一记录（journal 是时间线，会被后一条覆盖语义）
- 不写在对话里（对话会被压缩）

一本账。否则「这件事到底提过没有、对方回没回」就要翻三个地方。

## 2. 每条必须包含五件事

| 字段 | 要求 | 反例 |
|---|---|---|
| `impact` | 说不做会怎样，要具体到后果 | 「影响联调」 |
| `need` | **要对方做什么**，可以照做的动作 | 「沟通一下」「对齐一下」「同步一下」 |
| `due` | 何时需要（段号或里程碑） | 「尽快」 |
| `blocks` | 看板任务 id，被卡住的那几张 | 无，或写卡标题 |
| `evidence` | 依据：契约章节、行号、或对方提交 | 「之前说过」 |

`need` 的写法标准只有一条：**对方看完可以直接动手，不需要再问我一句「你具体要什么」**。写不成这样就说明事情还没想清楚，不该登记。

`blocks` 必须是真实存在的任务 id。它存在的意义是让「哪张卡被哪件事卡住」可查，而不是靠读描述猜——`board:check` 会校验 id 存在，且**未闭环的协作项不许阻塞一张已 done 的卡**（那说明状态自相矛盾）。

## 3. 四态

| 状态 | 含义 | 谁能推进到下一态 |
|---|---|---|
| `blocking` | 卡我开工，没有它我这条线动不了 | 对方回复后转 `answered` |
| `waiting` | 等对方回，但不卡我当前单元 | 对方回复后转 `answered` |
| `answered` | 已回，待我落地实现 | 我实现并验证后转 `closed` |
| `closed` | 已闭环 | — |

`closed` **必须能定位**：提交哈希、`§章节号`、或具体行号，三者至少一个。

这条被变异测试打过一次：第一版写的是「证据里含『已』字」，结果任何中文句子都能过，等于没检查。**闭环不能靠语气词证明。**

## 4. 我不替对方改契约

契约真源在运营端仓库（`admin/Docs/ops-api-contract.md`）。发现缺口：

1. 记一条 `COLLAB`，`type` 写「裁决」或「回写」，`need` 写明我需要的结论
2. 我自己按**当前契约**实现，不按我以为的应该
3. 同时在 `2026-10-30-ops-alignment.md` 记 DIF 编号
4. 对方改了正文 → 我复核行号 → 转 `closed`

**不直接在对方文件里改**。改了就没人知道那是谁的决定，下次漂移时也找不到源头。

## 5. 推进时机

- **每段开工**：先扫 `blocking` 项。有就说明这段不该开工，去催或改计划。
- **每段收口**：检查本段是否产生新的 `answered`（对方回了但我没落地）——这类最容易被忘。
- **里程碑节点**：`due` 与本段相关的项，逐条给四态，不许合并成一句「在等他们」。

## 6. 检查

```bash
pnpm board:check
```

校验：id 唯一 · 状态与类型合法 · 五字段齐全 · `need` 不是空话 · `blocks` 指向真实任务且不与 done 冲突 · `closed` 可定位。

检查失败**改数据，不改脚本**——放宽检查等于把这一页重新变成装饰。
