# 长任务推进协议

适用于**跨多个工作段连续推进**的成批任务（当前是 ops 主线 ~46 个单元 + 业务 backlog）。这份文件是**节奏与止损**约束，不排任务顺序——顺序在 `Docs/superpowers/plans/2026-10-30-long-run.md`。

短任务（一段内能收口的事）不必套用本协议。

## 1. 任务卡不是工作单位

任务卡是**目标**，推进单元（Unit）是**一刀**。一张卡可能 1 刀也可能 6 刀。

切分唯一标准：**这一刀能否独立提交并通过全部门禁**。

- 切不动（要碰表外文件、要等另一个单元的表）→ 说明切分错了，重切，不扩边界。
- 一段内收不了口 → 说明粒度太大，再切一刀。
- 不设「做到 80% 的单元」。**长任务最容易死在一堆半成品上**：既不能提交也不能丢弃。

## 2. 单元五步，不可跳步

| 步 | 动作 | 判据 |
|---|---|---|
| 1 入口 | 读最近一份 journal 的 `## 断点`；`pnpm board:check`；`git status` 干净 | 断点缺失先补断点，不动代码 |
| 2 实施 | 只碰单元声明的文件 | 越界即停 |
| 3 单元验证 | 只跑本单元的 pgTAP / 单测 / 集成 | 红则改实现 |
| 4 全量门禁 | 11 道一起跑（§3） | 红则定位 |
| 5 收口 | 1 提交 + 看板状态 + 实测数字 + journal `## 断点` | 四者缺一不算收口 |

一个提交对应一个单元。**不允许「顺手把下一单元也改了」**——那会让回退失去边界。

## 3. 门禁必须全量

```
pnpm board:check && pnpm format:check && pnpm format:sql:check && pnpm lint \
  && pnpm schema:check && pnpm check:deploy && pnpm typecheck && pnpm test \
  && pnpm build && pnpm db:local:verify && pnpm db:local:http
```

- 不许跑子集后宣布通过。**.vue 文件不在 `tsc` 覆盖范围内**，只有 `vue-tsc` 才看得见模板类型错误。
- 数字取自当次输出。引用历史数字等同于编造。
- 门禁红**不改门禁**：改实现，或改断言并说明断言本身错在哪。放宽阈值、加 `--no-verify`、跳过用例都属于改门禁。

## 4. 绿不是证据

每段末**抽 1 条**本段新增的关键断言做变异验证：故意改坏实现，确认它变红。

不红说明这条断言没测到东西，等于没写。

> 已踩过两次：`vitest` fork worker 静默启动失败吞掉 15 条断言仍报「38 文件全过」；幂等第一枪变异写成 `return [scope.key]`（每次新数组）导致缓存永远失效，反而没测到命名空间。

## 5. 断点协议

journal 每单元末尾追加，格式固定：

```markdown
## 断点（YYYY-MM-DD HH:MM）
- 本单元：
- 已完成：
- 未完成：
- 下一单元：
- 阻塞：
- 环境：迁移 N 个；pgTAP M 文件 K 断言
```

下一段开工**先读断点，不读对话**。对话会被压缩，journal 不会。

## 6. 止损

| 情形 | 处理 |
|---|---|
| 同一单元门禁红 3 次 | 停，写问题登记（现象 / 已排除 / 下一步假设），转下一单元 |
| 一段内定位不了 | 回退到单元入口，不留半成品 |
| 契约与实现冲突 | 记 DIF 台账，不改运营端契约正文 |
| 需要运营端先动作 | 登记为前置点，**能绕行就绕行开工**，不等 |

## 7. 跨层不许并行

ops 的 11 个域是数据链不是模块清单（客户→合同→应收→收款→权益；报表读全部）。下层形状未定就写上层，测试只能对 mock 断言，等于把桩的问题搬进后端。

并行的正确位置是**同一域内的不同刀**（S1 schema 收口后，S2 契约与 S3 端点可不同段做），或**与主线零交叉的填缝任务**。
