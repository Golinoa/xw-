## 关键决策

### 1. 字典的读不要 `settings.manage`——这是 §5.9 唯一明确放开的一条

`GET /dictionaries` 的权限列写的是「任意已认证运营成员」。数字上它只是个读端点，
但取舍很具体：字典里装的是「问题类型有哪些选项」，而创建工单的人需要这个下拉。
若按写权限一起收，等于把一个下拉框锁给了管理员——现象是工单创建页里那一格
永远是空的，而没有人会把它和权限联系起来。

写（`POST`/`PATCH`）仍要 `settings.manage`。两条线方向相反，所以测试必须成对：
G1 断言商务读设置页被拒（42501），G2 断言同一个商务读字典成功。只测一侧会把
「下拉框被锁」当成正常。

### 2. 三行参数 vs 契约的单数 `updatedBy`

`ops.settings` 是「一参数一行」，三行各有 `updated_by` / `updated_at`，而契约给
的是单数。三种可能：返回三份（前端显示三个「谁改的」）、返回最新的那一份、或者
再加一张变更表。

选「最新的那一份」，语义是「这张设置页最后一次被谁动过」。第三种方案（变更表）
其实更准，但它要一张新表 + 每次都写一行，而这一页真正的问题只有「上次是谁动的」
——为它建历史表是把成本放在错的地方。

顺带定了 `updatedBy` 为空时的语义：种子行的 `updated_at` 是迁移落库的时间、
`updated_by` 是 NULL，前端据此显示「初始值」。**用 `updated_at IS NULL` 判「从没
改过」是错的**——种子一插它就有值。这一条最初写成了断言 `updated_at` 为 NULL，
在真库上立刻红了。

### 3. PATCH 是部分对象，不是「三个字段都确认一遍」

只改一个键时把另外两个原样传下去，看起来无害（值没变），但两个人在设置页上各改
一项时会互相覆盖：A 把窗口改成 45，B 只改工时、请求体里带着自己加载时的窗口 30，
于是 A 的修改被 B 静默回滚。这类丢失不出错、不留痕。

所以 patch 只放「真的传了的键」，SQL 侧按 `jsonb_object_keys` 逐个落库。

### 4. 字典的 `value` 没有白名单 CHECK，这是「字典」与「枚举」的分界

如果把 `payment_methods` 的取值写进 CHECK，它就不是字典了：运营改一个词要发版。
字典的权威在表里，前端下拉从 `GET /dictionaries` 取。

代价要说清：消费方**不会**被库层拦住。`ops.tickets.issue_type` 只要求非空字符串，
它创建时不会去字典里核对。收严（改成「必须在字典内」）会拒掉历史上下文中合法但
不常见的值，属于跨域改动，已记在 C-121 一并请裁决。

同理，条目**停用而不是删除**：删掉之后历史行回显成裸 `value`，停用还能查到
`label`。所以没有 `DELETE` 端点，也没有 `dictionary.deleted` 这个审计词。

### 5. 越界回 400 且带 `field`，表上的 CHECK 仍然保留

表上的 CHECK 报的是 `settings_value_check` 这种约束名，前端没法据此把某个输入框
标红。所以函数里先按字段判一次范围，返回 `{status:'out_of_range',field,min,max}`。

CHECK 不删：将来有迁移直接写这张表时，它是唯一管得住的地方。「同一件事判两次」
在这里是对的——两次判的目的不同（一次为了可读的错误、一次为了不可绕过的保证）。

### 6. 字典两表按既有形态落地，没按契约 §7.3 的 A1 开直写

契约 §7.3 把 `dictionaries` / `dictionary_items` 归在 A1（`authenticated` 直写
白名单列 + RLS 写策略）。业务端从 o-t04 起对**所有** ops 表执行
`REVOKE ALL ... FROM authenticated` + RLS 无策略，写入一律经 `SECURITY DEFINER`
RPC。也就是说 A1 与 A2 在库里长得一样。

这一轮没有为字典破例开直写：同一个 schema 里两种写路径会让「谁能写这张表」变成
要查两处的问题，而 RPC 形态顺带保住了「权限 + 审计在同一事务里」。偏差记在
C-120，请契约侧修订矩阵或指出哪几张表真要开直写。

## 踩坑

### 断言写错方向，被真库打回来

`S3` 最初写成「`updatedAt` 为 NULL 表示从没改过」。种子行一插就有 `updated_at`，
于是它在真库上立刻红了——这类错误在纸面上看不出来，因为「从没改过」这个说法
本身没错，错的是拿哪一列表示它。

### 直接在 `authenticated` 身份下读新表

`D10` 最初直接 `select from ops.dictionary_items` 验「改文案不改值」，被 42501
挡住（那正是 G4 要单独断言的事）。改成走 `list_dictionaries` 按 `value` 找到条目、
再看它的 `label`——这既是前端会走的路径，也让断言多了一层意思：`value` 若被改掉，
这条会查到 null。

### 变异第一枪指出一处「会写错行」的隐患

去掉「未知键整体拒绝」之后，未知键会走到逐键落库的 `case ... else` 分支，落到
`retention.exportDays` 上：一个拼错的字段名（`retentionDays`）会被当成对
导出保留天数的合法修改，值还正好是 30。这不是「被忽略」，是**写错了行**。

## 未验证 / 遗留

1. **导出三个端点仍未做**（异步任务、签名下载、`export.read` / `export.create`
   分离、导出写审计、`ops.exports` 表）。这是 o-t13 的最后一块。
2. **`out_of_range` / `unknown_key` 两个信封在 HTTP 层不可达**：zod 的 strictObject
   与 min/max 先挡住，SQL 那两个分支只对「绕过端点直接打 RPC」的调用生效。单元
   测试里分开写了「被 zod 挡住（且没打到 RPC）」与「信封翻译」两条，避免下一个人
   以为 RPC 分支有测试守着。
3. **`payment_methods` 目前没有消费方**：`ops.receipts` 没有「方式」列，这个字典
   是先备着的。是否本期就要，见 C-121。
4. **`ops.tickets.issue_type` 不做字典校验**（见决策 4），已记 C-121。
5. **`dictionaries` 没有「新建字典」端点**：契约 §5.9 只给了三个端点，字典本身由
   迁移植入。因此「码不存在」一律回 404 而不是顺手新建——这条是对的，但也意味着
   加一组字典要发版，已在 C-121 里一并说明。
