# 2026-10-31 · 导出任务（o-t13 第四块，域收口）

## 这一单元做了什么

`o-t13` 的四块（总览、报表、设置页、导出）到最后一块。三个端点 + 一个执行器：

```
GET  /exports              列表（顺带推进一条待办）
POST /exports              202 + queued
GET  /exports/{exportId}   详情（succeeded 时签下载地址）
```

`ops.exports` 表、`export_no` 序列、十个 RPC（发起/列表/详情/认领/取数/完成/
失败/过期扫描 + 两个纯函数）都是本轮新建。

最终数字：36 迁移 / 28 个 pgTAP 文件 / 1197 条断言（本域 40）；集成 20 文件
377 例；单测 60 文件 786 例；build 主 chunk 1,638.77 kB 无增长。13 道门禁全绿。

## 关键决策

### 1. 「谁发起的」决定数据范围，「谁在看」决定能不能下载

导出是唯一一种把数据变成**文件**的端点：文件会被转发、被存到桌面、被三个月后
翻出来。所以这一域有两条不同方向的权限判定，而它们必须分开：

- **取数时按 `exports.requested_by` 判域读权限。** 不做这一条，一个只有
  `export.create` 的财务就能把工单全表导出去——`ticket.read` 这道门等于不存在。
  这条也顺便让懒执行成立：触发者是谁不影响结果，只有发起人是谁影响。
- **签下载地址时按当前请求者的域读权限判。** `get_export` 返回 `can_download`，
  路由据此决定给不给 `downloadUrl`。有 `export.read` 的人能看见任务（列表是
  `export.read`），但看不见内容。

两处方向相反是有意的：任务归属决定「这份文件是谁要的」，域权限决定「这份数据谁
能看」。把它们合成一条（比如「只能看自己发起的」）会同时错两次——管理员看不到
别人发起的任务，而一个被撤权的发起人仍然能下载自己的旧文件。

### 2. 懒执行：没有队列的环境里，只写不跑的任务就是幽灵

本地栈与刚部署的线上都没有 worker。`GET /exports` 与 `GET /exports/{id}` 各自
先认领并跑掉**一条**最早的任务，再返回。代价是一次列表请求可能多花几百毫秒；
换来的是「没有幽灵 queued」。

`claim_export` 顺手做两件事：把超出租约的 `running` 放回队列，取最早一条改成
running。租约借的是 `expires_at`——运行中这一列没有别的用处（前端只在 succeeded
时展示），加一列 `started_at` 只为记一个「可能卡住的开始时间」不划算。代价是
`finish_export` 必须把它改写成真正的产物过期时间，否则一份刚成功的导出会立刻
显示「已过期」。

不加租约的后果不是理论上的：API 进程在上传文件时被重启，那一行会永远 `running`，
既不会被重试也不会被标失败，前端一直转圈。

### 3. 复用各域 `list_*` 函数，而不是另写一套 where

导出与列表口径分叉过一次就再也对不上，而错法是「导出的行数比列表少两行」这种
没人会立刻发现的样子。所以 `export_fetch_rows` 直接调 `list_receivables` /
`list_receipts` / `list_tickets` / `list_contracts` / `list_customers`，翻页循环，
一次 500 行。

代价是导出受列表函数的分页上限约束：`list_contracts` / `list_customers` 把
page_size 钳到 100，所以那两个域每轮只取 100 行。pgTAP 里有一条断言把这件事
钉住：**同一份筛选，导出的 `row_count` 必须等于列表的 `total`**（F3）。

另一面是预算：超过 100000 行直接失败（`too_many_rows`），不截断。一份静默少了
几万行的导出比一次明确的失败危险得多——看数字的人不会怀疑文件本身。

### 4. CSV 的列名是数据库列名，不是 DTO 的 camelCase

契约说 `filters` 与列表端点同构，但**没说产物长什么样**。选了「数据行直出」：
列名用 `customer_no` 而不是 `customerNo`，嵌套对象是 JSON 字符串。

理由与第 3 条同源：为五个域各维护一份「DTO 列名 + 嵌套展开规则」的映射表，是
第二真源，而且它一定会落后于 DTO 的改动。要中文表头或固定列序，应该另做一层
「报表模板」，而不是把 DTO 形状塞进导出。取舍记在 C-125，请契约侧裁决。

### 5. 失败必须落成 `failed`，且不能把读请求打成 5xx

执行器的每一条失败路径都翻成一次 `abort_export`（原因进审计），而不是只打日志：
停在 `running` 的任务会让前端永远转圈，而「任务失败」正是用户需要知道的事。
反过来，执行失败**不能**让列表 500——用户要在列表里看到「这条失败了」，而不是
一个错误页。`runPendingExports` 整个函数不抛。

`ops.exports` 没有 `failure_reason` 列（契约 §3.9 的列清单里没有），所以失败原因
只存在于审计的 `after_summary.reason` 与 API 日志里。这是有意的取舍：多一列就是
一张契约外的表，而失败原因不需要被列表查询。记 C-126。

## 踩坑

### 约束自相矛盾，被过期扫描抓出来

第一版的 `exports_object_only_when_succeeded` 写的是「只有 `succeeded` 可以有
storage_path / row_count」。但保留期到了之后 `succeeded → expired` 这条 UPDATE
自己就被它挡住了——`expired` 行必须留着产物路径，否则清理任务找不到文件、
页面也说不出「它曾经在哪」。

pgTAP 的 X1 一跑就红（`violates check constraint`）。约束要回答的是「谁有产物」，
不是「谁现在还能下载」；后者由状态与 `can_download` 一起回答。改成
`status IN ('succeeded','expired')`。

**这类错误的形状值得记住**：约束写的是状态机的一条边，而状态机有后继状态。
写约束时要想的不是「当前成功的那个状态」，而是「哪些状态代表文件存在」。

### 断 BOM 不能断字符串

集成测试里先写的是 `(await download.text()).charCodeAt(0) === 0xfeff`，收到的是
`13`（`\r`）。不是实现没写 BOM，而是 **WHATWG 的 UTF-8 解码会剥掉前导 BOM**：
`Response.text()` 拿到的字符串永远没有它。

改成断字节（`arrayBuffer()` 的前三字节是 `EF BB BF`），再用
`new TextDecoder('utf-8', { ignoreBOM: true })` 解码。BOM 是给 Excel 看的，
不是给解码器看的——这条差别只在「断言写错方向」时才暴露，而它会让人去改实现。

### 同事务里 `now()` 恒定，按 `created_at` 排序没有意义

pgTAP 的每个文件是一个事务，`now()` 返回事务开始时间。于是同一文件里创建的多条
导出 `created_at` 完全相同，`ORDER BY created_at LIMIT 1` 拿到的是任意一条。
表现是断言时灵时不灵——比稳定红更糟。

两处修：`list_exports` 与 `claim_export` 的排序都加 `export_no` 作次级键（它单调
递增）；测试里所有「最早的那条」都改成按 `export_no` 定位。

顺带发现序列不随事务回滚：同一个文件跑第二遍单号就往后走了。所以断言里任何
「硬编码 `EXP-000001`」的写法都会在第二遍之后红，改成与单号无关的固定值。

### 一条恒真的断言，只有变异才能证明它没用

补完「取数切到发起人身份」之后，顺手加了一条断言：让 `ops_viewer`（有
`customer.read`、没有 `customer.sensitive.read`）当发起人、管理员当触发者，
断言导出回包里不含联系人 `phone` 原值。

它一直是绿的。按流程做变异——把实现里的 `set_config('request.jwt.claims', …)`
整段去掉，让取数回到触发者身份——**断言还是绿的**。原因很朴素：`customer_list_json`
的 `primary_contact` 只拼 `masked_phone` / `masked_email`，原值根本不在列表回包里，
所以「谁在取数」对输出没有影响。

这条断言删了。留下的是一条迁移注释，写明这层切换是结构保证、今天不可观测、
因此没有断言——**这比一条假的绿有用**。变异在这里的价值不是「发现 bug」，而是
「发现测试没在测它想测的东西」。

### 顺序写错的 stub 会让测试假绿

单测的 fetch stub 里，我把「签名上传」的分支写在「PUT 上传」之前。签名地址本身
也含 `/object/upload/sign/`，于是 PUT 被当成又一次「要签名」，**上传请求一次都没
发出去**，而两个用例仍然是绿的（只断言了 RPC 顺序）。后来加「PUT 必须发生」的
断言才露出来。

这是 stub 的典型失效方式：它替你完成了一个你正在测的动作。

## 未验证 / 遗留

1. **`too_many_rows` 分支没有在真库触发过。** 要 10 万行才能走到，pgTAP 里造不出
   这个量级。分支逻辑只有代码可读，没有断言守着。
2. **真实规模下的执行耗时未知。** 契约 §10.1 要求 100k 应收下列表 p95 < 800ms，
   但「导出 100k 行 + 拼 CSV + 上传」这条链路没有压过。懒执行意味着它会挂在某个
   用户的读请求上——如果真的慢，体验是「列表页偶发卡顿」。
3. **`running` 租约到期后重跑没有覆盖「上传成功但 finish 失败」的窗口**：文件已经
   在存储里，状态却被放回队列，下一次会再传一份（同 key，覆盖）。结果是幂等的，
   但会多一次上传。属可接受，未写断言。
4. **「以发起人身份取数」这一层今天不改变任何输出，因此没有断言守着它。**
   五个域的列表函数里没有一个按会话分支，`customer_list_json` 的
   `primary_contact` 恒为掩码值。我先写了一条断言（用 `ops_viewer` 做发起人、
   管理员做触发者，断言回包里没有 `phone` 原值），然后按变异流程把实现里的
   身份切换去掉——断言**仍然绿**。也就是说它测的不是这件事，是一条恒真的假
   断言，已删除。这层切换保留为结构保证，理由写在迁移注释里。
5. 前端三个页面（列表、创建、下载）未做，属运营端范畴。

  但今天五个域的列表路径都没有按会话分支，所以这个选择不可观测；请契约侧
  确认「导出以发起人视角取数」是口径而不是实现细节。
