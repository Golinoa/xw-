## 三条设计决定

1. **`blocks` 存看板任务 id，不写卡标题**。这样「哪张卡被哪件事卡住」可查，且能被命令校验：未闭环的协作项若阻塞一张已 done 的卡，直接报错——那是状态自相矛盾的硬信号。
2. **`need` 不许以「沟通/对齐/同步」开头**。判断标准只有一条：对方看完能直接动手，不需要再问一句「你具体要什么」。写不成这样，说明事没想清楚。
3. **`closed` 必须可定位**：提交哈希、`§章节号`、或行号。

## 变异测试打穿了一处

第一版证据检查写的是 `HASH.test(...) || /§|第 N 行|L\d+|已/.test(...)`。最后那个 `已` 字几乎任何中文句子都有，等于没检查。

三枪变异里两枪红、一枪绿：

- `need` 改成「沟通一下」→ 红 ✓
- `blocks` 加不存在的 id → 红 ✓
- 未闭环却阻塞已 done 的卡 → 红 ✓
- `closed` 但证据只写「他们…已按真端点实现」→ **绿，说明形同虚设** ✗

改成 `LOCATOR = /[0-9a-f]{7,40}|§\s*\d|第\s*\d+\s*行|\bL\d+/` 后复测变红。**闭环不能靠语气词证明。**

顺带记录一个自己的错：第一轮变异三枪全绿，不是检查的问题，是我的变异脚本 `node -e "..." "$case"` 拿错了 argv 下标（`node -e` 下参数从 argv[1] 起），三个用例一条都没改到文件。变异不生效时的现象和不设防一模一样——这本身就值得警惕。
