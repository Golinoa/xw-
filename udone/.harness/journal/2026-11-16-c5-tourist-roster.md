# C5 游客名单

日期：2026-11-16 · 卡片：C5（P1）· 出口：名单 CRUD + 证件去重 + CSV 预览/整批原子

## 问题

订单里只有 `adult_count` / `child_count` 两个申报数字，谁上了团、证件号是多少全在纸面上。
需求 §6 要的不只是「能录名字」，而是三件事同时成立：

1. 同一个人不能在一张单里出现两次（按证件类型 + 证件号判定）；
2. 没有证件号的人不能被「自动合并」——两个没登记号码的老人不是一个人；
3. CSV 导入要么全进，要么一个都不进，因为部分成功之后没人能说清补哪些。

## 决策

1. **不新增 `tourist.*` 权限，复用 `order.read` / `order.write`。**
   名单是订单聚合的一部分。另立权限会造出「有 order.write 却改不了自己单子的名单」
   这种没有任何业务含义的组合，而且还要在三个角色的矩阵里再解释一遍为什么。
2. **可见性继承订单，不自己抄规则。** 策略是
   `EXISTS (SELECT 1 FROM public.orders WHERE id = tourists.order_id)`——那个子查询
   同样受 orders 的 RLS 约束，于是组织隔离、`order.read`、`own` 数据范围、软删除
   四条规则自动生效。抄一份条件在这里，等于把同一份规则维护两遍，日后放宽订单可见性
   时必然漏改一处。
3. **去重键用生成列 + 部分唯一索引。**
   `normalized_document_number` 由数据库算（去空白、去连字符、统一大写），
   唯一索引建在它上面，并带 `WHERE ... IS NOT NULL`：空号码在唯一索引里互不相等，
   正好表达「没有号码就没有可比的身份证」。规范化不能交给调用方——CSV 里
   `110101-19900101-1234` 与 `110101199001011234` 是同一个人的两种写法，这是最常见的差异。
4. **有号码必须有类型（CHECK）。** 去重键是 `(类型, 号码)` 两维；只填号码会让护照与
   身份证同号（现实中存在）被误判成同一个人。
5. **PATCH 改号码必须同时给类型。** 否则「号码换了、类型还是旧的」，人还是那个人，
   去重键却落在旧类型上。这一条在契约层做，不进服务层——服务层判不出来「用户是不是想改一半」。
6. **导入走库函数，不在服务层拼两次 PostgREST 调用。** 覆盖模式是「先删后插」，
   两次 HTTP 之间 Worker 可能被回收，名单就没了。plpgsql 函数体是一个事务，
   一行失败连 DELETE 一起回滚。函数用 SECURITY INVOKER（默认）：读走 orders 的 RLS，
   写走 tourists 自己的策略，越权在最后一道防线仍然拦得住。
7. **组织 id 由函数从订单里取，不让调用方传。** 传进来的组织 id 只要和订单不一致就是
   复合外键违规；而「从订单取」让跨组织写根本没有参数可填。
8. **模板只有表头，没有示例行。** 示例行看起来友好，但它会被老实导入成一个叫「张三」的
   游客——线上没人会先把示例删掉。取值说明放在导入弹窗里。
9. **模板是 JSON 里的 filename + content，不是 `text/csv` 端点。** 后者要绕过
   `respond()`，而「所有出站响应都过契约校验」这条规则一旦有例外，以后每个下载接口都会跟着例外。
10. **预览与提交共用同一段解析代码，提交时重新解析。** 前端提交的仍然是那份原始 CSV，
    服务端每次都重算；前端改不动结果，也不会出现「预览全绿、提交报错」。
11. **格式错误 400、证件重复 409。** 两者都要改文件，但改法不同：前者改写法，后者要么删行、
    要么换成覆盖模式。合成一个码，前端只能给一句没用的「提交内容不合法」。
12. **名单不分页。** 一个团的游客是有限集合（几十人），与订单的应收/应付明细同一处理；
    分页会让「一眼看到全团」变成翻页操作。

## 验证

| 门禁 | 结果 |
| --- | --- |
| pgTAP | **36 文件全绿**（44 个迁移），新增 `tourist_roster.sql` 17 条断言 |
| 单元测试 | **63 文件 / 849 用例**（改前 61 / 819） |
| 类型检查（api + web） | 0 错误 |
| eslint + CSS token | 通过 |
| HTTP 集成 | **24 文件 / 402 用例**（新增 `tests/integration/tourists.test.ts` 11 条） |

**变异验证**：把部分唯一索引换成 `SELECT 1` 后重跑 pgTAP，`tourist_roster.sql` 变成
「通过 10 / 失败 7」——重复证件被接受、名单人数从这行开始全部错位、批内重复不再中止、
覆盖模式把老名单真的删掉了。改回后全绿。这条链路说明唯一索引不只是「防重」，
它还是导入原子性的最后一道闸。

**为什么值得单独写 HTTP 集成用例**：`rpc/import_tourists` 的参数名（`requested_order_id` /
`requested_mode` / `requested_rows`）、返回列名（`inserted_count` / `deleted_count`）、
以及 23505→409 的映射，全都发生在 PostgREST 一侧。pgTAP 只能证明 SQL 是对的，
证明不了「HTTP 上真的这么调」。集成用例里还专门验了「覆盖模式在批内重复时名单人数不变」
——那是本卡最贵的一条语义，只有真跑过才知道回滚生效。

**前端行为不在自动门禁内**：名单表格、导入弹窗、模板下载、掩码输入框锁定这几条只有
类型保证，没有人点过。

## 未做

- **名单导出**：属于 C8（R-REPORT-01 报表与导出）的范围，且导出要按权限决定证件号明文/掩码，
  与本卡的掩码规则共用一个入口才合理。
- **游客与客户档案的关联**：需求没要求。同一客户再报名是另一张订单，名单行不复用——
  名单记录的是「这一团都有谁」，不是客户档案的副本。
- **名单进「编辑订单」表单**：编辑是整单替换语义，把名单混进去会让「只改金额」也重写名单。
  名单只在详情抽屉里维护。
- **导入的「人数差额」拦截**：需求明确只警告不阻断，所以差额只是提示文案。
- **附件/护照扫描件**：R-FILE-01 明确不在首期范围。

## 顺手发现（不在本卡范围）

1. **`updated_by` 又是「列在、没人写」。** `tourists` 有这一列，但服务层只写 `updated_at`。
   与 C4 记录的 `routes` / `customers` / `sources` / `tags` 完全同一个问题：审计链上少一环
   「谁改的」。修它要么统一加 BEFORE UPDATE 触发器，要么把 `userId` 传进每个仓储——跨模块，
   本轮不动。
2. **规范化规则是两份实现**（TS `normalizeDocumentNumber` 与 SQL 生成列）。这是刻意接受的
   重复：唯一真源在库里，而「预览时判断会不会撞人」需要应用侧先算一遍。两侧各有测试钉住，
   任何一侧改动都会让另一侧变红。彻底消除需要把预览也交给库函数（多一次往返），
   不值得。
3. **C4 遗留的一处 prettier 格式缺陷**（`OrderFormModal.vue` 里一个多行 `a-button` 该收成一行），
   顺手修掉了——同一批文件，一行改动，不修会让 `format:check` 一直红。
