# 2026-10-31 · 跨域拒绝与回归（o-t14）

## 这一单元做了什么

契约 §7.4 那张 13 行的拒绝表，第一次有了**逐行对应**的文件。三样东西：

- `supabase/tests/ops_cross_domain_denials.sql`（33 条断言）：表里 RLS 层的
  P1–P5、P7–P10、P13，一行一节，节号就是行号；外加 §0 两条表驱动断言扫
  「授权面」和「函数 EXECUTE 面」。
- `tests/integration/ops-denials.test.ts`（3 例）：表里 API 层的 P11、P12。
  这两条原文写的是「**任意** ops 端点」，所以遍历 `OPS_ROUTES` 的全部 120 条，
  而不是挑几个代表。
- `scripts/generate-db-schema.mjs` 加了两条迁移版本号校验（唯一 + 14 位形态）。

顺手修了一个真实缺口：`ops.entitlement_snapshot_immutable()` 保留了函数默认 ACL，
**PUBLIC（因而 anon）可执行**。新迁移 `20261031000014_ops_trigger_function_revoke.sql`
补掉。

最终数字：37 迁移 / 29 个 pgTAP 文件 / **1230** 条断言（本文件 33）；集成 21 文件
**380** 例；单测 60 文件 786 例；build 主 chunk 1,638.77 kB 无增长。13 道门禁全绿。

## 关键决策

### 1. 这张表必须有人认领，而且必须有人按行对账

各域的 `ops_*_domain.sql` 里也有 P1–P4 编号，但那是**域内**编号：本域没权限能不能
读本域数据。§7.4 不一样，它是**跨域**的——P9 讲运营身份读不到租户业务表、P10 讲
不借用租户上下文、P7/P8 讲审计与核销两张表不可改删。这些问题没有哪个域愿意认领，
因为它们测的不是「这个域对不对」，而是「两套身份体系有没有串线」。

没有专人认领的断言，迟早会在某次重构里被顺手删掉，而且删掉之后没有任何测试会红。
所以这个文件按契约表格逐行建节，**读它的人和读契约的人看到同一个顺序**。域内测试
可以被重写，这个不行。

代价是它和域内测试有重复（比如 P7 在 `ops_identity_rls.sql` 里已经有一条）。这个
重复是买来的：它保证「契约说什么」与「我们证明了什么」两件事可以逐行对照，而不用
在 29 个文件里拼图。

### 2. 契约的「期望」全对，三条「括注」写的机制在本实现里不存在

§7.4 每一行有两部分：期望（结果）和括注（机制）。结果全部成立，但三条括注描述的
是另一套设计：

| 行 | 括注说的机制 | 本实现的机制 |
| --- | --- | --- |
| P3 | 有列级 INSERT 授权，`WITH CHECK` 为 false | 表级零授权；42501 |
| P5 | `select ops.receipts` 返回 0 行 | 表级零授权；读走 RPC，RPC 判权限 |
| P13 | `status` 不在 UPDATE 列白名单 | 连表级 UPDATE 都没有 |

全域 `grep 'GRANT .*UPDATE ('` 零命中：ops 业务表对 `authenticated` 是**表级零授权**，
读也走 `SECURITY DEFINER` RPC。所以默认状态下这三条的形状是 42501，不是 0 行，
也不是策略违例。

这不是「契约写错了」，是契约描述的是设计意图，实现在 P5/P13 上走得更远（连门都不
开，而不是开半扇再拦）。处理办法不是把断言写成 42501 了事——那样第二道门（RLS
开着、策略为零 = 默认拒绝）就再也没人检查，哪天有人 `DISABLE ROW LEVEL SECURITY`
排查问题、事后忘了开回来，所有测试照样绿。

所以每条都测两遍：先钉默认态（42501），再**临时补授**相应权限，证明第二道门真的
在挡。临时授权只活在本事务里，跑完即回滚。变异 3 就是对这一层的验证：关掉
`ops.customers` 的 RLS 之后，恰好三条断言变红（P3 的 WITH CHECK、P13 的零行、
P13 的行值未变），别的都不动。

### 3. P9 的正确定义是「指名道姓也要不到」

第一版 P9 只让运营身份 `count(*) from public.orders`。这一版改成**两种身份都显式
带上同一个 `x-organization-id` 头**：运营身份直接指名道姓要那家租户的数据，仍然
拿 0 行，才是这条证明的意思。不带这个头的话，「0 行」还可以解释为「他没说要哪家」
——那是另一件事，而且是没有威胁模型的那一件。

### 4. 迁移版本号的重复不由 CLI 兜底

T-14 的验收里有一条「空库全量重放成功且迁移版本号无重复」。前半条由 `db:local:verify`
的 `replay()` 天然覆盖（每次 DROP 重建）；后半条没有任何门禁管。

supabase CLI 遇到重复版本号时不会报错，它跑其中一个。两个同号迁移在本地按文件名
排序看起来都对，到线上只跑了一个——症状是「这个字段本地有、线上没有」，而没有任何
一处日志说迁移被跳过了。所以把「唯一 + 14 位形态」写进 `generate-db-schema.mjs`，
跟着 `schema:check` 走。形态那条的理由是字典序：`2026...` 与 `20261031...` 混排之后
迁移顺序会静默改变。

### 5. 表驱动的 401/403 扫描：两百多个请求买一个全称命题

P12 的原文是「无 token 调用**任意** ops 端点 → 401」。域内测试只能证存在量词——
每个域都有一条 `token: ''` → 401，但没有任何一条会因为你**新加的第 121 个端点忘了
挂 `requireOpsAuth`** 而变红。漏挂的那个端点自己不会写测试，它的域也还没建。

所以遍历全表。变异 4 验证了它有效：把 `GET /ops/exports` 的 `requireOpsAuth()` 删掉，
三条断言全红（401 扫描、403 扫描、逃逸检查），失败信息直接点名
`GET /api/v1/ops/exports → 500`。

一个细节：断言写成「非 401 的必须落在白名单里」（子集），而不是「恰好等于白名单」。
原因是 `POST /auth/refresh` 没有 cookie 时由**处理函数自己**回 401，与中间件回的那个
从外部完全同形。要相等就得给它编一个能走通的请求，那样测的是刷新逻辑，不是鉴权面。

### 6. 函数 EXECUTE 面也扫全集，扫出一个真缺口

「ops 下所有函数都不给 public/anon」是 T-02 就写下的验收断言，但没有任何门禁在查它。
表驱动一扫：120 个函数里有 1 个还留着默认 ACL ——`ops.entitlement_snapshot_immutable()`，
权益域建的触发器函数，那个迁移末尾 20 多条 `REVOKE` 里恰好漏了它。

今天不可利用（触发器函数不能直接调用；anon 也没有 schema USAGE），但它破坏的是
「全量成立」这个前提。留着这一个例外，等于把异常当成默认接受——下一个人写 REVOKE
清单时会照着这份漏过的样子抄。

## 变异验证（四枪）

| # | 变异 | 期望 | 实际 |
| --- | --- | --- | --- |
| 1 | `GRANT EXECUTE … TO public` 给那个触发器函数 | A2 函数面红 | 仅 #3 红（have 1 / want 0） |
| 2 | `current_organization_id()` 不再校验成员身份 | P9 红 | **全绿** — 见下 |
| 2b | 再加 `has_permission` 恒真 + `current_data_scope` 恒 `all` | P9 红 | 仅 #25/#26/#27 红（各 have 1） |
| 3 | `ALTER TABLE ops.customers DISABLE ROW LEVEL SECURITY` | P3、P13 第二层红 | 恰好 #11/#32/#33 红 |
| 4 | 删掉 `GET /ops/exports` 的 `requireOpsAuth()` | 401/403 扫描红 | 3 例全红，点名该路由 |

**第 2 枪是本轮最有价值的一次失败。** 只关掉 `current_organization_id()` 的成员校验，
P9 三条断言**依然全绿**。原因不是断言写错了，而是 `public.orders` 的读策略有三个
条件并列：

```sql
organization_id = current_organization_id()
AND has_permission('order.read')
AND (current_data_scope() = 'all' OR created_by = auth.uid())
```

运营身份三条都不满足。换句话说 P9 的绿是**三重冗余**的结果，单点变异根本推不动它。
这有两面：

- 好的一面：租户侧的身份边界确实是纵深防御，坏掉一层还有两层。
- 需要写下来的一面：**P9 不是任何单一机制的测量**。它证明的是复合性质「运营身份
  读不到租户明细」，而不是「组织过滤有效」或「权限判定有效」。想要后者，得为每个
  条件单独写断言——那是租户侧测试的职责，不是这里的。

第 2b 枪（三重同时关闭）才让它红，且红得干净：只有 P9 那三条，P10 与其余全部不动。
这说明断言确实落在「身份」上，而不是「表恰好是空的」。

## 未验证 / 遗留

1. **`admin` 侧的两件交付物没做**：契约 T-14 的交付物里有「`admin` 侧契约差异检查
   脚本」与前端 `contract-version.ts` 守卫（§2.1.1 的 MAJOR 不一致时阻断渲染）。
   两者都在运营端仓库，不在 `udone` 的范围内。上卡。
2. **P6 没有搬进新文件**。它需要一条有联系人的客户夹具，而正反两面（有
   `customer.sensitive.read` 的人**能**看到原值）已经写在
   `ops-customers.test.ts` 的两条里。搬过来只会多一份会各自漂移的副本；新文件头部
   注明了 P6 的证据在哪。
3. **「恰好六个可读表」这条用的是数组相等**。加一张、删一张、改名一个都会红。这是
   有意的严格，但代价是：如果确实要给第七张表开 SELECT，得同时改迁移和这条断言，
   而失败信息只说「数组不等」，不说「你新开的那张是不是故意的」。评审时看 diff 才
   知道。
4. **401/403 扫描依赖 `resolveOpsContext` 每条都回库一次**，120 条路由约 0.5 秒
   （403 那一遍）。如果以后涨到 500 条路由，这个测试会成为集成套件里最慢的一个，
   届时要考虑按模块分组并发，而不是砍掉覆盖。
5. **`too_many_rows` 等导出遗留项**仍未变（见上一份 journal），本轮未触碰。

## 协作账本新增

- **C-128**：§7.4 的 P3/P5/P13 三条括注描述的是「列级授权 + `WITH CHECK` + UPDATE
  列白名单」，本实现全域没有列级授权（表级零授权 + `SECURITY DEFINER` RPC）。期望
  列（失败 / 0 行）成立，括注需要改写。建议改成「表级零授权，且 RLS 开启、策略为空
  ——两道门都关」。
- **C-129**：T-14 的交付物含 `admin` 侧契约差异检查脚本与前端 contract-version
  守卫，属运营端仓库，本轮未交付，需在运营端排期。
- **C-130**：`ops.entitlement_snapshot_immutable()` 曾保留 PUBLIC EXECUTE。根因不是
  手误，是「每个迁移末尾手抄一份 REVOKE 清单」这个做法本身——函数越多，抄漏的概率
  越高。是否改成按 `pg_proc` 扫描生成 REVOKE，或加一条「ops 下任何函数都不得有
  PUBLIC EXECUTE」的门禁（本轮的断言 #3 已经是这条门禁的雏形，但它只在 pgTAP 里跑，
  不在 CI 的静态门禁里）。
