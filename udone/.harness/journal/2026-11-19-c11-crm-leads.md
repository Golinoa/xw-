## 交付面

- 3 个迁移：
  - `crm_leads`：leads 表（阶段/负责人/预算/期望日期等完整字段）+ lead_events 时间线；
  - `crm_lead_followup`：建线索、跟进+阶段变更（每次追加事件）；
  - `crm_lead_pool`：认领、分配、7 天超时回收、幂等转客户。
- 契约：`crm.ts` + 7 个端点（列表/详情/新建/跟进/认领/分配/转换）。
- API：`/api/leads*`，读要 order.read、写要 order.write。
- Web：`/leads` 线索页，我的线索/公海切换、阶段筛选、新建、跟进、认领、转客户。
- 测试：pgTAP 8 断言、API 单测 5 条、HTTP 集成 5 条。

## 关键口径

1. **乐观锁**：认领/分配都带 `version`，`WHERE version = 期望值` 条件更新；
   两人同时点认领只有一个成功，另一个拿 409 VERSION_MISMATCH。
2. **超时回收**：`last_follow_up_at` 为空时按 created_at，超过 7 天回公海（owner_id = NULL）。
3. **幂等转换**：converted_customer_id 一旦写入就不再变，重复调用返回同一客户 id；
   按手机号归一化匹配既有客户，重复客户走关联而不是新建。
4. **事件时间线只追加**：leads/lead_events 不给 authenticated 直接写权限，所有写走 RPC，
   结构上保证「每次变更都留事件」。

## 踩过的坑（下次直接照做）

1. **`coalesce` 不能写 `pg_catalog.coalesce`**（与 C10 的 nullif 同类）：它是 SQL 构造。
2. **leads 表没有 UPDATE 策略**：pgTAP 里直接 UPDATE 造数据静默影响 0 行，
   要 `SET LOCAL ROLE postgres` 临时提权；测试完记得切回 authenticated。
3. **回收后 owner 为 NULL 就不能再跟进**：record_lead_follow_up 要求当前用户是负责人，
   测试里回收后要先认领回来。
4. `routes.ts` 里新增 `z.object(...)` 需要把 `import type { z }` 改成值导入。
